# 클린 아키텍처 (Clean Architecture)

> **TL;DR**
> 클린 아키텍처는 비즈니스 로직을 데이터베이스, UI, 프레임워크로부터 격리해서 변경이 안전하게 퍼지도록 하는 계층형 설계 방식이다.

---

## 클린 아키텍처를 왜 쓰는지 감 잡기

웹 프레임워크를 교체하거나 데이터베이스를 바꿀 때, 비즈니스 로직까지 같이 고쳐야 한다면 설계가 잘못된 것이다. 클린 아키텍처는 "핵심 업무 규칙"을 가장 안쪽에 두고, 외부 기술 세부사항(DB, HTTP, UI)은 바깥쪽으로 밀어낸다. 바깥 계층은 안쪽을 알지만, 안쪽 계층은 바깥을 모른다. 이 단방향 의존 규칙 하나가 전체 구조를 안정적으로 만든다.

처음 배울 때는 이렇게 이해하면 된다.

`핵심 흐름: 엔티티(Entity) → 유스케이스(Use Case) → 인터페이스 어댑터 → 프레임워크/드라이버`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 엔티티 (Entity) | 업무 규칙 그 자체. 어떤 프레임워크도 DB도 모른다. 예: `Order`, `Customer` 클래스. |
| 유스케이스 (Use Case) | 엔티티를 조합해서 실제 기능을 수행하는 단위. 예: `PlaceOrder`, `ProcessPayment`. |
| 인터페이스 어댑터 | 유스케이스가 원하는 데이터 형식과 DB/웹이 사용하는 형식 사이를 변환하는 층. |
| 의존성 규칙 | 코드의 의존 방향은 항상 안쪽(엔티티)을 향해야 한다. 바깥이 안쪽을 알면 안 된다. |
| 경계 (Boundary) | 계층 사이의 인터페이스. 안쪽 계층은 인터페이스만 정의하고 구현은 바깥에 둔다. |

## 예를 들어 설명하면

이커머스 시스템을 예로 들면 각 계층이 이렇게 나뉜다.

```
[프레임워크/드라이버]   Spring MVC 컨트롤러, JPA Repository 구현체, MySQL 연결
        |
[인터페이스 어댑터]    ProductRepositoryImpl, OrderController, DTO 변환
        |
[유스케이스]           AddProductToCart, PlaceOrder, ProcessPayment
        |
[엔티티]               Product, Order, Customer (순수 Java/Kotlin 클래스)
```

`ProductRepository`는 유스케이스 계층에 인터페이스로 선언된다. 실제 DB 접근 코드(`ProductRepositoryImpl`)는 가장 바깥 계층에서 그 인터페이스를 구현한다. 덕분에 유스케이스를 테스트할 때 DB 없이 가짜(Mock) 구현체를 꽂으면 된다.

## 이 단계에서 중요한 판단 기준

유스케이스 코드에 `import org.springframework.*` 같은 프레임워크 의존이 보인다면 의존성 규칙이 깨진 것이다.

## 한 줄 요약 — 이것만 기억하면 된다

**비즈니스 로직은 데이터베이스와 프레임워크를 몰라야 한다. 방향은 항상 안쪽으로.**

## 나중에 더 깊게 들어가면

- 헥사고날 아키텍처(포트-어댑터)와 클린 아키텍처의 차이
- 유스케이스 계층에서 트랜잭션 경계를 어디에 둘 것인가
- 모노리스에서 마이크로서비스로 전환할 때 계층 경계를 어떻게 쪼개는가
