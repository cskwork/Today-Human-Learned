# 템플릿 엔진이 있는데 왜 React를 쓰는가

> **TL;DR**
> 템플릿 엔진은 서버가 HTML을 완성해 보내고, React는 브라우저에서 UI를 직접 제어한다. 상호작용이 많을수록 React가 낫다.

---

## 이 주제를 왜 이해해야 하는지 감 잡기

EJS 같은 템플릿 엔진도 동적인 페이지를 만든다. 그런데 왜 React가 따로 존재할까. 핵심 차이는 "누가, 언제 HTML을 만드느냐"다. 템플릿 엔진은 서버가 요청마다 HTML을 완성해서 브라우저에 보낸다. React는 최소한의 HTML만 보내고, 이후 화면 변경을 브라우저 안에서 처리한다.

버튼 클릭 한 번으로 목록이 바뀌는 화면을 생각해 보자. 템플릿 엔진은 서버에 다시 요청해 새 HTML 전체를 받아야 한다. React는 변경된 부분만 화면에서 바꾼다.

`핵심 흐름: [템플릿 엔진] 요청 → 서버 렌더링 → 전체 페이지 전송 / [React] 초기 로드 → 브라우저에서 상태 변경 → 부분 업데이트`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 서버 사이드 렌더링(SSR) | 서버가 HTML을 완성해서 보내는 방식. 템플릿 엔진이 여기 해당 |
| 클라이언트 사이드 렌더링(CSR) | 브라우저가 JS를 실행해 화면을 그리는 방식. React의 기본 동작 |
| SPA (Single Page Application) | 페이지를 새로 받지 않고 한 HTML 안에서 화면을 교체하는 앱 구조 |
| 컴포넌트 | React에서 UI를 조각으로 나눈 단위. 재사용 가능한 함수나 클래스 |
| 상태(State) | 컴포넌트가 기억하는 데이터. 상태가 바뀌면 화면이 자동으로 갱신된다 |

## 예를 들어 설명하면

같은 아이템 목록을 EJS와 React로 구현할 때 구조 차이다.

EJS는 서버에서 목록을 완성해 보낸다.

```ejs
<!-- views/index.ejs -->
<ul>
  <% items.forEach(item => { %>
    <li><%= item %></li>
  <% }) %>
</ul>
```

React는 브라우저에서 목록을 렌더링하고, 항목이 추가되면 서버 왕복 없이 화면만 바꾼다.

```jsx
function ItemList({ items }) {
  return (
    <ul>
      {items.map(item => <li key={item}>{item}</li>)}
    </ul>
  );
}
```

항목을 실시간으로 추가하거나 필터링하는 기능이 필요하다면, 매번 서버에 요청하는 템플릿 엔진 방식은 느리고 복잡해진다.

## 이 단계에서 중요한 판단 기준

페이지 전환이나 사용자 상호작용이 단순하면 템플릿 엔진으로 충분하고, 실시간 업데이트나 복잡한 상태 관리가 필요하면 React를 선택한다.

## 한 줄 요약 — 이것만 기억하면 된다

**템플릿 엔진은 정적 콘텐츠 중심 페이지에, React는 상호작용이 많은 앱에 적합하다.**

## 나중에 더 깊게 들어가면

- Next.js가 SSR과 CSR을 함께 지원하는 방식
- React의 상태 관리 도구 (useState, Redux, Zustand)
- 템플릿 엔진 방식이 SEO에 유리한 이유와 React에서의 SSR 대안
