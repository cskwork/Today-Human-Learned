# 소프트웨어 엔지니어링 핵심 법칙

> **TL;DR**
> 개발 현장에서 반복되는 실패 패턴 12가지를 이름 붙여 놓은 것이 소프트웨어 엔지니어링 법칙이다. 정답지가 아니라 "지금 우리가 어떤 함정에 빠지고 있는지" 빠르게 알아보게 해주는 렌즈다.

---

## 이 주제를 왜 쓰는지 감 잡기

기능은 늘었는데 구조는 더 복잡해지고, 사람을 더 뽑았는데 일정은 더 밀리며, 코드 커버리지는 높은데 버그는 줄지 않는다. 이런 상황이 반복된다면 기술 선택 문제가 아니라 구조적 패턴의 문제일 가능성이 높다.

오랜 시간 개발 현장에서 관찰된 이 패턴들이 법칙으로 정리됐다. 알고 있으면 문제를 발견했을 때 해결책을 찾기 전에 먼저 "어떤 법칙이 작동하고 있는가"를 묻게 된다.

`핵심 흐름: 반복 문제 발생 → 법칙으로 이름 붙이기 → 패턴 인식 → 적절한 대응 선택`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| Conway's Law | 시스템 구조는 팀의 커뮤니케이션 구조를 닮는다 — 팀 경계를 바꾸면 아키텍처도 달라진다 |
| Hyrum's Law | API 사용자가 충분히 많아지면, 문서에 없는 동작도 누군가는 의존한다 — 작은 변경도 예상 밖 장애를 낼 수 있다 |
| Brooks's Law | 늦어진 프로젝트에 사람을 더 투입하면 더 늦어진다 — 온보딩 비용과 커뮤니케이션 부하가 늘기 때문이다 |
| Goodhart's Law | 지표가 목표가 되는 순간, 그 지표는 더 이상 좋은 지표가 아니다 |
| YAGNI | "You Aren't Gonna Need It" — 지금 필요하지 않은 기능은 만들지 않는다 |

## 예를 들어 설명하면

법칙은 회의에서 문제에 이름을 붙이는 데 즉시 쓸 수 있다.

| 상황 | 해당 법칙 | 해석 |
|---|---|---|
| API 응답 필드 순서를 바꿨더니 고객사 장애가 발생 | Hyrum's Law | 문서화되지 않은 동작도 누군가는 의존한다 |
| 초기부터 마이크로서비스로 나눴는데 배포가 더 어려워짐 | Gall's Law | 단순한 시스템으로 먼저 검증한 뒤 복잡도를 키워야 했다 |
| 코드 커버리지 90%인데 핵심 버그는 계속 발생 | Goodhart's Law | 지표가 목적을 대체하고 있다 |
| 일정 지연으로 개발자를 추가했는데 기존 팀원이 설명하느라 더 바빠짐 | Brooks's Law | 인력 추가가 병목을 해결하지 못한다 |

## 이 단계에서 중요한 판단 기준

법칙은 해결책이 아니라 진단 도구다. 문제가 생겼을 때 해결책을 먼저 말하기 전에, 어떤 법칙이 작동하고 있는지 이름을 붙이는 것이 더 빠른 길이다.

## 한 줄 요약 — 이것만 기억하면 된다

**좋은 팀은 코드를 잘 짜는 팀이 아니라, 구조와 일정과 지표를 함께 관리할 줄 아는 팀이다.**

## 나중에 더 깊게 들어가면

- CAP Theorem: 분산 시스템에서 일관성(Consistency), 가용성(Availability), 분할 허용성(Partition tolerance) 중 무엇을 우선할지 정하는 방법
- Hofstadter's Law: 예상보다 오래 걸린다는 사실을 고려해도 여전히 오래 걸리는 이유, 그리고 일정 버퍼 설계 방법
- Law of Leaky Abstractions: 프레임워크가 내부 복잡성을 완전히 숨길 수 없는 이유와 이를 대비하는 방법
