# 컴파일과 인터프리팅: 소스 코드가 실행되기까지

> **TL;DR**
> 소스 코드를 CPU가 읽을 수 있는 기계어로 바꾸는 방법은 두 가지다. 컴파일러는 먼저 전체를 번역하고, 인터프리터는 한 줄씩 번역하면서 바로 실행한다.

---

## 컴파일과 인터프리팅을 왜 알아야 하는지 감 잡기

CPU는 0과 1로 된 기계어(바이너리)만 이해한다. 우리가 작성하는 Python이나 C 코드는 사람이 읽기 좋게 쓴 것이고, 이것을 기계어로 옮기는 번역 작업이 반드시 필요하다. 이 번역을 언제, 어떻게 하느냐에 따라 언어의 실행 속도, 배포 방식, 디버깅 경험이 크게 달라진다. 컴파일러 방식과 인터프리터 방식을 구분하면 언어를 선택할 때 근거 있는 판단을 할 수 있다.

초보자는 처음에 이렇게 이해하면 된다.

`소스 코드 작성 → 번역기(컴파일러 or 인터프리터) → 기계어 → CPU 실행`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 기계어(Machine Code) | CPU가 직접 실행할 수 있는 0과 1의 이진 명령어. 사람이 읽기 어렵지만 컴퓨터는 이것만 이해한다. |
| 컴파일러(Compiler) | 소스 코드 전체를 읽어 실행 파일(.exe 등)로 미리 변환하는 번역기. 한 번 번역하면 이후에는 번역 없이 실행한다. |
| 인터프리터(Interpreter) | 소스 코드를 한 줄씩 읽어 즉시 실행하는 번역기. 실행할 때마다 번역을 반복한다. |
| 렉서/토크나이저(Lexer/Tokenizer) | 소스 코드를 의미 있는 단위(토큰)로 쪼개는 컴파일러의 첫 단계. 영어 문장을 단어로 나누는 것과 같다. |
| 바이트코드(Bytecode) | 기계어도 소스 코드도 아닌 중간 형태. Java가 컴파일 후 생성하는 .class 파일이 여기에 해당하며 JVM이 이것을 해석해 실행한다. |

## 예를 들어 설명하면

컴파일러와 인터프리터의 차이를 비교하면 다음과 같다.

| 구분 | 컴파일러 | 인터프리터 |
|---|---|---|
| 번역 시점 | 실행 전 전체 번역 | 실행 중 한 줄씩 번역 |
| 실행 속도 | 빠름 (번역 비용 없음) | 느림 (매번 번역) |
| 배포 | 바이너리 파일 배포 (소스 비공개 가능) | 소스 코드 혹은 인터프리터 필요 |
| 오류 발견 | 실행 전 컴파일 오류로 발견 | 실행 중 해당 줄에 도달해야 발견 |
| 대표 언어 | C, C++ | Python, Ruby |

Java는 두 방식을 결합한다. 소스를 컴파일해 바이트코드(.class)를 만들고, JVM이 이것을 인터프리팅(또는 JIT 컴파일)해서 실행한다. 플랫폼 독립성과 성능을 동시에 얻기 위한 선택이다.

## 이 단계에서 중요한 판단 기준

성능이 최우선이고 배포 환경이 고정돼 있으면 컴파일 언어를, 빠른 피드백과 플랫폼 유연성이 중요하면 인터프리터 언어를 선택한다.

## 한 줄 요약 — 이것만 기억하면 된다

**컴파일러는 미리 전부 번역해서 속도를 얻고, 인터프리터는 한 줄씩 번역하면서 유연성을 얻는다 — Java는 그 둘을 절충한 대표 사례다.**

## 나중에 더 깊게 들어가면

- JIT(Just-In-Time) 컴파일러: 인터프리터의 속도 단점을 런타임 최적화로 보완하는 방식
- 컴파일러 내부 단계: 렉서 → 파서 → AST → 코드 생성
- Python의 CPython 구현이 실제로 바이트코드를 생성하고 PVM이 이를 실행하는 과정
