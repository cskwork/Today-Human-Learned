# MongoDB — 유연한 문서 저장소가 왜 필요한가

> **TL;DR**
> MongoDB는 행과 열 대신 JSON 형태의 문서로 데이터를 저장하는 NoSQL 데이터베이스로, 구조가 제각각인 데이터를 다룰 때 관계형 DB보다 훨씬 편하다.

---

## MongoDB를 왜 쓰는지 감 잡기

관계형 데이터베이스는 스프레드시트처럼 모든 행이 같은 열을 가져야 한다. 그런데 현실 데이터는 그렇지 않은 경우가 많다. 사용자 A는 전화번호가 있고, 사용자 B는 SNS 계정이 있고, 사용자 C는 기업 고객이라 담당자 목록까지 붙는다. 이런 데이터를 관계형 DB에 억지로 우겨넣으면 NULL로 가득 찬 열이 생기거나, 테이블을 여러 개로 쪼개야 한다.

MongoDB는 각 데이터를 독립적인 문서(document)로 저장한다. 문서마다 구조가 달라도 된다. 스키마를 미리 확정하지 않아도 되니, 개발 초기에 데이터 구조가 자주 바뀌는 프로젝트에 잘 맞는다.

`핵심 흐름: 문서(Document) → 컬렉션(Collection) → 데이터베이스(Database)`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| Document | 하나의 데이터 단위. JSON처럼 키-값 쌍으로 구성된다 |
| Collection | 관계형 DB의 테이블에 해당. 문서들의 묶음인데, 구조를 강제하지 않는다 |
| BSON | MongoDB가 내부적으로 쓰는 바이너리 JSON. 날짜, 바이너리 등 JSON에 없는 타입도 지원한다 |
| Sharding | 데이터를 여러 서버에 나눠 저장하는 수평 확장 방식 |
| Index | 특정 필드로 빠르게 검색할 수 있도록 미리 만들어두는 색인 |

## 예를 들어 설명하면

블로그 플랫폼을 만든다고 하자. 관계형 DB라면 게시글, 댓글, 태그를 각각 별도 테이블로 분리하고 JOIN으로 합쳐야 한다. MongoDB에서는 게시글 하나를 하나의 문서에 통째로 담을 수 있다.

```json
{
  "title": "MongoDB 첫 인상",
  "author": "kim",
  "tags": ["database", "nosql"],
  "comments": [
    { "author": "lee", "text": "잘 읽었습니다." }
  ],
  "publishedAt": "2024-05-27T12:00:00Z"
}
```

같은 컬렉션 안에 댓글이 없는 문서, 태그가 없는 문서가 섞여 있어도 오류가 나지 않는다. 이 유연성이 MongoDB의 핵심이다.

## 이 단계에서 중요한 판단 기준

데이터 구조가 자주 바뀌거나 중첩된 배열/객체를 자주 저장해야 한다면 MongoDB를 검토하고, 복잡한 JOIN과 트랜잭션 무결성이 핵심이라면 관계형 DB를 먼저 고려한다.

## 한 줄 요약 — 이것만 기억하면 된다

**MongoDB는 스키마를 강제하지 않는 문서 저장소로, 구조가 유동적인 데이터를 빠르게 다루는 데 적합하다.**

## 나중에 더 깊게 들어가면

- Aggregation Pipeline: 데이터 집계와 변환을 파이프라인으로 처리하는 방법
- Replica Set: 고가용성을 위한 복제 구성
- 트랜잭션: MongoDB 4.0 이후 다중 문서 ACID 트랜잭션 지원 범위와 한계
