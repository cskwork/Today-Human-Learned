# Redis — 왜 이렇게 빠른가

> **TL;DR**
> Redis는 모든 데이터를 RAM에 올려두기 때문에 디스크 기반 DB보다 수십~수백 배 빠르고, 다섯 가지 자료구조로 대부분의 캐싱 문제를 해결한다.

---

## Redis를 왜 쓰는지 감 잡기

일반적인 데이터베이스는 데이터를 디스크에 저장한다. 디스크에서 데이터를 읽는 속도는 메모리보다 수천 배 느리다. 페이지 요청이 초당 수만 건 들어오는 서비스에서 매번 DB를 조회하면 병목이 생긴다. Redis는 이 문제를 단순하게 해결한다 — 자주 쓰는 데이터를 RAM에 올려두고, 거기서 직접 읽는다. 평균 응답 시간 1ms 미만이 가능한 이유다. 캐싱, 세션 저장, 실시간 순위표, 메시지 브로커에 주로 쓴다.

초보자는 처음에 이렇게 이해하면 된다.

`핵심 흐름: 클라이언트 요청 → Redis(RAM) 조회 → 없으면 DB → Redis에 저장 후 반환`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 인메모리 | 데이터를 디스크가 아닌 RAM에 저장하는 방식. 빠르지만 전원이 꺼지면 사라질 수 있다. |
| TTL (Time To Live) | 키에 만료 시간을 설정하는 기능. 세션처럼 일정 시간 후 자동 삭제가 필요할 때 쓴다. |
| RDB | 특정 시점의 전체 데이터 스냅샷을 파일로 저장하는 영속성 방식. |
| AOF | 모든 쓰기 명령을 로그 파일에 순서대로 기록하는 영속성 방식. RDB보다 데이터 손실이 적다. |
| Eviction | 메모리가 꽉 찼을 때 오래된 데이터를 자동으로 지우는 정책. maxmemory 설정과 함께 쓴다. |

## 예를 들어 설명하면

쇼핑몰에서 상품 목록은 자주 바뀌지 않지만 요청은 초당 수천 건이다. Redis에 캐싱하면 DB 부하를 대폭 줄인다.

```
SET product:list "[{...}]"       # 상품 목록 저장
EXPIRE product:list 3600         # 1시간 후 자동 만료
GET product:list                 # 캐시에서 즉시 반환
```

다섯 가지 자료구조와 주요 용도는 아래와 같다.

| 자료구조 | 대표 명령어 | 언제 쓰나 |
|---|---|---|
| String | SET / GET | 캐싱, 카운터 |
| List | LPUSH / RPOP | 작업 큐, 최신 항목 목록 |
| Set | SADD / SMEMBERS | 고유 항목 집합, 태그 관리 |
| Sorted Set | ZADD / ZREVRANGE | 순위표, 점수 기반 정렬 |
| Hash | HSET / HGETALL | 사용자 프로필, 객체 표현 |

## 이 단계에서 중요한 판단 기준

Redis는 RAM을 쓰므로 저장할 데이터 크기를 반드시 계산하고, maxmemory와 eviction 정책을 설정해두지 않으면 서버가 OOM으로 다운될 수 있다.

## 한 줄 요약 — 이것만 기억하면 된다

**Redis는 RAM 기반이라 빠르고, 다섯 가지 자료구조로 캐싱부터 실시간 순위표까지 단일 도구로 해결한다.**
