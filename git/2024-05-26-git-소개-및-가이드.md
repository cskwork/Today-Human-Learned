# Git — 버전 관리 시스템 기초

> **TL;DR**
> Git은 코드 변경 이력을 스냅샷으로 기록해 두었다가, 필요할 때 되돌리거나 팀원과 안전하게 합치는 분산 버전 관리 도구다.

---

## Git을 왜 쓰는지 감 잡기

코드를 혼자 짜다 보면 "어제까지는 됐는데 오늘 뭔가 망가졌다"는 상황이 생긴다. 그때 `app_v2_final_진짜최종.py` 같은 파일을 만들게 된다. Git은 이 문제를 해결하기 위해 만들어졌다. 모든 변경 사항을 커밋(commit)이라는 단위로 기록해 두고, 언제든지 과거 시점으로 되돌아갈 수 있다.

팀에서 쓰면 더 강력하다. 여러 사람이 동시에 같은 파일을 수정해도 Git이 충돌(conflict)을 감지하고, 어느 쪽 변경을 반영할지 결정할 기회를 준다.

초보자는 처음에 이렇게 이해하면 된다.

`핵심 흐름: 수정(Working Directory) → 선택(Staging Area) → 저장(Local Repository) → 공유(Remote)`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 커밋(Commit) | "지금 이 상태를 사진 찍어 저장한다"는 행위. 나중에 이 시점으로 돌아올 수 있다. |
| 브랜치(Branch) | 본 작업에 영향 없이 실험하거나 기능을 추가할 수 있는 독립된 작업 공간. |
| 스테이징(Staging) | 커밋할 변경 사항을 미리 골라 담아두는 임시 바구니. `git add`로 담는다. |
| 원격 저장소(Remote) | GitHub, GitLab 같이 인터넷 서버에 올려둔 공용 저장소. 팀원과 공유하는 장소. |
| 병합(Merge) | 두 브랜치의 변경 사항을 하나로 합치는 작업. 충돌이 없으면 자동, 있으면 수동 해결. |

## 예를 들어 설명하면

새 기능을 만드는 전형적인 흐름이다.

```bash
# 저장소 초기화
git init

# 파일 작성 후 스테이징
git add app.py

# 스냅샷 저장
git commit -m "feat: add initial app"

# 기능 브랜치 생성 후 이동
git checkout -b feature/logging

# 기능 구현 → 커밋
git add app.py
git commit -m "feat: add logging"

# 메인 브랜치로 돌아와 병합
git checkout main
git merge feature/logging

# 팀원과 공유
git push origin main
```

브랜치를 쓰면 메인 코드에 손대지 않고 실험할 수 있다. 실험이 실패하면 브랜치를 버리면 그만이다.

## 이 단계에서 중요한 판단 기준

커밋은 작고 자주 — 한 번에 기능 하나, 파일 몇 개 수준이어야 나중에 이력을 읽을 수 있고 문제 발생 시 범위가 좁아진다.

## 한 줄 요약 — 이것만 기억하면 된다

**Git은 코드에 "실행 취소 무제한"과 "팀 협업"을 동시에 제공하는 도구다.**

## 나중에 더 깊게 들어가면

- 브랜치 전략: git-flow vs GitHub Flow vs Trunk-Based Development
- 충돌(Conflict) 해결 방법과 `rebase` vs `merge` 차이
- 커밋 메시지 규칙(Conventional Commits)과 이력 관리
