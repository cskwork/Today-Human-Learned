# Nginx — 가볍고 강력한 웹 서버

> **TL;DR**
> Nginx는 이벤트 기반 비동기 구조로 적은 메모리로 수만 개의 동시 연결을 처리하며, 정적 파일 서빙·리버스 프록시·로드 밸런싱을 하나의 설정 파일로 제어한다.

---

## Nginx를 왜 쓰는지 감 잡기

웹 서버는 클라이언트(브라우저)의 요청을 받아 파일이나 애플리케이션 응답을 돌려주는 소프트웨어다. Apache처럼 오래된 서버는 요청 하나당 프로세스(또는 스레드) 하나를 만들어서 처리한다. 동시 접속자가 수천 명이 되면 프로세스가 폭발적으로 늘어나 메모리가 바닥난다. Nginx는 이 문제를 이벤트 루프로 해결한다. 소수의 워커 프로세스가 비동기로 수만 개의 연결을 논블로킹으로 처리하기 때문에 리소스 효율이 훨씬 높다.

초보자는 처음에 이렇게 이해하면 된다.

`핵심 흐름: 클라이언트 요청 → Nginx(정적 파일 직접 반환 또는 백엔드 전달) → 백엔드 응답 → 클라이언트`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 리버스 프록시(Reverse Proxy) | 클라이언트와 백엔드 서버 사이에 앉아서 요청을 대신 전달하는 중간 서버. 클라이언트는 백엔드 주소를 모른다. |
| 워커 프로세스(Worker Process) | Nginx가 실제 요청을 처리하는 프로세스. 보통 CPU 코어 수만큼 띄운다. |
| upstream | 로드 밸런싱 대상 백엔드 서버 그룹을 정의하는 블록. 여기에 서버를 나열하면 Nginx가 분산해서 보낸다. |
| SSL 터미네이션 | HTTPS 암호화/복호화를 Nginx가 담당하고, 내부 백엔드에는 평문 HTTP로 전달하는 방식. |
| location 블록 | URL 경로 패턴별로 다른 동작을 정의하는 Nginx 설정 단위. |

## 예를 들어 설명하면

세 개의 백엔드 서버로 트래픽을 나누는 로드 밸런서 설정:

```nginx
upstream backend {
    server backend1.example.com:8080;
    server backend2.example.com:8080;
    server backend3.example.com:8080;
}

server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

설정을 바꾼 뒤에는 `nginx -t`로 문법 오류를 먼저 확인하고, `nginx -s reload`로 무중단 적용한다.

## 이 단계에서 중요한 판단 기준

정적 파일은 Nginx가 직접 서빙하고, 동적 처리가 필요한 요청만 백엔드로 넘기는 구조가 가장 효율적이다.

## 한 줄 요약 — 이것만 기억하면 된다

**Nginx는 이벤트 기반 비동기 구조로 적은 리소스로 높은 동시 접속을 처리하며, 리버스 프록시와 로드 밸런싱까지 한 곳에서 담당한다.**

## 나중에 더 깊게 들어가면

- 로드 밸런싱 알고리즘 선택 (least_conn, ip_hash, weighted round robin)
- proxy_cache를 이용한 응답 캐싱과 TTL 관리
- DNSSEC, HTTP/2, gRPC 프록시 지원 설정
