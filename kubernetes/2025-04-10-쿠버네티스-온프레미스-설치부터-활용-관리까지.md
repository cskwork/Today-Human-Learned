# 쿠버네티스 온프레미스 — 자체 서버에 클러스터 구축하기

> **TL;DR**
> 쿠버네티스를 클라우드 대신 자체 서버에 직접 설치할 때 알아야 할 핵심 개념, 도구 선택, 사전 준비를 정리한다.

---

## 온프레미스 쿠버네티스를 왜 쓰는지 감 잡기

AWS EKS나 GKE 같은 관리형 서비스는 클러스터 운영의 많은 부분을 클라우드 업체가 대신 해주지만, 데이터 주권 문제나 규제 요건, 장기 비용 최적화가 필요한 경우라면 자체 서버에 쿠버네티스를 직접 구축하는 선택을 한다.

온프레미스 방식은 하드웨어부터 컨트롤 플레인까지 모든 것을 직접 관리한다. 설정 자유도는 가장 높지만, 그만큼 운영 책임도 전적으로 사용자에게 있다.

초보자는 처음에 이렇게 이해하면 된다.

`서버 준비 → 사전 설정 → 설치 도구 선택 → 컨트롤 플레인 초기화 → 워커 노드 추가 → 앱 배포`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 컨트롤 플레인 | 클러스터 전체를 관리하는 두뇌. 어떤 파드를 어느 노드에 올릴지 결정한다. |
| 워커 노드 | 실제 컨테이너(파드)가 실행되는 서버. |
| kubeadm | 쿠버네티스 공식 설치 도구. `kubeadm init`으로 클러스터를 초기화한다. |
| CNI 플러그인 | 파드 간 네트워크 통신을 담당하는 컴포넌트. Calico, Flannel 등이 있다. |
| kubectl | 클러스터에 명령을 내리는 CLI 도구. 파드 조회, 배포, 로그 확인 모두 여기서 한다. |

## 예를 들어 설명하면

kubeadm으로 클러스터를 구축하는 핵심 흐름이다. 모든 노드에 스왑을 비활성화하고 컨테이너 런타임을 설치한 뒤 아래 순서를 따른다.

```bash
# 1. 마스터 노드 초기화
sudo kubeadm init --pod-network-cidr=192.168.0.0/16

# 2. kubectl 사용 설정 (출력된 안내 그대로 실행)
mkdir -p $HOME/.kube
sudo cp /etc/kubernetes/admin.conf $HOME/.kube/config

# 3. CNI 플러그인 설치 (Calico 예시)
kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.26.0/manifests/calico.yaml

# 4. 워커 노드에서 클러스터 참여 (init 후 출력된 토큰 사용)
sudo kubeadm join <컨트롤플레인-IP>:6443 --token <token> --discovery-token-ca-cert-hash sha256:<hash>
```

설치 도구를 먼저 선택해야 한다.

| 도구 | 적합한 상황 |
|---|---|
| Minikube | 단일 노드, 로컬 학습 및 명령어 연습 |
| K3s | 빠른 멀티 노드 구성, 엣지/리소스 제한 환경 |
| kubeadm | 표준 방식, 운영 수준 클러스터, 깊은 학습 |

## 이 단계에서 중요한 판단 기준

설치 전 모든 노드에서 스왑 비활성화(`swapoff -a`)와 필수 포트 개방(API 서버 6443, kubelet 10250, NodePort 30000-32767)을 반드시 확인한다. 이를 빠뜨리면 설치 후 원인 불명의 오류가 발생한다.

## 한 줄 요약 — 이것만 기억하면 된다

**온프레미스 쿠버네티스는 하드웨어 준비부터 CNI 선택까지 직접 결정해야 하지만, 그 대신 완전한 제어권을 얻는다.**

## 나중에 더 깊게 들어가면

- etcd 백업과 컨트롤 플레인 고가용성(HA) 구성
- Persistent Volume과 온프레미스 스토리지(Ceph, NFS) 연동
- Ingress 컨트롤러와 MetalLB를 이용한 온프레미스 로드 밸런서 설정
