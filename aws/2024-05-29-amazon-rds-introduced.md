# Amazon RDS — 데이터베이스 운영 잡무를 AWS에 맡기는 방법

> **TL;DR**
> RDS는 MySQL·PostgreSQL 같은 관계형 데이터베이스를 AWS가 대신 설치·백업·패치·복제해주는 완전 관리형 서비스다. 개발자는 쿼리에만 집중하면 된다.

---

## Amazon RDS를 왜 쓰는지 감 잡기

직접 EC2 위에 MySQL을 설치하면 이런 일들을 스스로 해야 한다. OS 패치, DB 버전 업그레이드, 야간 백업 스크립트 작성, 디스크 용량 모니터링, 장애 시 복구. 이 작업들은 본질적으로 앱 기능과 무관하지만 하지 않으면 데이터를 잃는다.

RDS(Relational Database Service)는 이 운영 잡무 전체를 AWS가 대신한다. 개발자는 DB 엔진 종류와 인스턴스 크기만 고르면, 나머지는 자동화된다. 전문 사서 팀을 고용해 도서관 관리를 맡기는 것에 가깝다.

초보자는 처음에 이렇게 이해하면 된다.

`핵심 흐름: DB 엔진 선택 → 인스턴스 크기 설정 → Multi-AZ 여부 결정 → 앱에서 엔드포인트로 연결`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 완전 관리형 서비스 (Managed Service) | 백업·패치·하드웨어 교체 등 운영 작업을 AWS가 자동으로 처리해주는 방식 |
| DB 인스턴스 | RDS에서 실행 중인 데이터베이스 서버 한 대 |
| Multi-AZ | 같은 데이터를 다른 가용 영역(물리적으로 분리된 데이터센터)에 자동 복제해 장애 시 자동 전환하는 고가용성 옵션 |
| 자동 백업 (Automated Backup) | RDS가 매일 스냅샷을 찍고 보존 기간 동안 보관하는 기능. 특정 시점으로 복구(PITR) 가능 |
| Amazon Aurora | AWS가 만든 클라우드 최적화 DB 엔진. MySQL·PostgreSQL 호환이면서 성능이 최대 5배 높다 |

## 예를 들어 설명하면

이커머스 서비스를 운영한다고 가정하자.

- DB 엔진: MySQL 8.0
- 인스턴스: db.t3.medium (개발) / db.r6g.large (운영)
- Multi-AZ: 활성화 — 주 인스턴스가 다운되면 수 분 내 예비 인스턴스로 자동 전환
- 자동 백업: 매일 오전 3시, 7일 보존
- 스케일업: 트래픽 증가 시 콘솔에서 인스턴스 타입 변경 → 수 분 후 적용

앱 코드에는 RDS가 제공하는 엔드포인트 주소(예: `mydb.xxxx.ap-northeast-2.rds.amazonaws.com`)를 연결 문자열로 넣으면 된다. 장애 시 엔드포인트 주소는 바뀌지 않으므로 앱 코드를 고칠 필요도 없다.

## 이 단계에서 중요한 판단 기준

RDS를 도입할 때 가장 먼저 결정해야 할 것은 Multi-AZ 활성화 여부다. 운영 환경에서 DB 다운타임이 허용되지 않는다면 Multi-AZ는 선택이 아니라 필수다.

## 한 줄 요약 — 이것만 기억하면 된다

**RDS는 DB 설치·백업·복제·패치를 AWS가 자동 관리하는 서비스로, 운영 부담 없이 관계형 데이터베이스를 쓸 수 있게 해준다.**

## 나중에 더 깊게 들어가면

- Read Replica: 읽기 부하를 분산하기 위해 복제본 인스턴스를 추가하는 방법
- 파라미터 그룹: DB 엔진 설정값(max_connections 등)을 코드로 관리하는 방법
- RDS Proxy: Lambda 같은 서버리스 환경에서 DB 연결 수를 효율적으로 관리하는 방법
