# Amazon CloudFront — 전 세계 사용자에게 콘텐츠를 빠르게 전달하는 CDN

> **TL;DR**
> CloudFront는 전 세계 엣지 로케이션에 콘텐츠 사본을 캐시해두고, 사용자에게 가장 가까운 곳에서 제공해 응답 속도를 높이는 AWS의 CDN 서비스다.

---

## CloudFront를 왜 쓰는지 감 잡기

서울에 있는 S3 버킷에 이미지를 저장해두면, 브라질 사용자가 그 이미지를 요청할 때마다 데이터가 서울에서 브라질까지 왕복해야 한다. 물리적 거리가 그대로 지연(latency)으로 나타난다.

CloudFront는 이 문제를 캐싱으로 해결한다. 전 세계 400곳 이상의 엣지 로케이션(소규모 데이터센터)에 콘텐츠 사본을 복사해두고, 사용자가 요청하면 가장 가까운 엣지에서 바로 응답한다. 브라질 사용자는 서울이 아닌 상파울루 엣지에서 이미지를 받는다.

초보자는 처음에 이렇게 이해하면 된다.

`핵심 흐름: 사용자 요청 → 가장 가까운 엣지 로케이션 → 캐시 히트면 즉시 응답 / 미스면 오리진 fetch → 캐시 저장 → 응답`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 엣지 로케이션 (Edge Location) | CloudFront가 콘텐츠를 캐시해두는 전 세계 곳곳의 소규모 데이터센터 |
| 오리진 (Origin) | 원본 콘텐츠가 있는 곳. S3 버킷, EC2, 외부 HTTP 서버 모두 가능 |
| 배포 (Distribution) | "어떤 오리진에서 어떤 콘텐츠를 어떻게 캐시할지" 정의하는 CloudFront 설정 단위 |
| TTL (Time to Live) | 엣지에 캐시된 콘텐츠가 유효한 시간. 만료되면 CloudFront가 오리진에서 새로 가져옴 |
| 캐시 히트율 (Cache Hit Ratio) | 전체 요청 중 엣지 캐시에서 바로 응답한 비율. 높을수록 오리진 부하와 지연이 줄어든다 |

## 예를 들어 설명하면

이미지·CSS·JS를 S3에 저장한 쇼핑몰 예시다.

```
[일본 사용자]
    |
[도쿄 엣지 로케이션]
    ├── 캐시 히트: 즉시 응답 (수 ms)
    └── 캐시 미스: 서울 S3에서 fetch → 도쿄 엣지 캐시 → 응답
```

CloudFront 배포를 만들 때 S3 버킷을 오리진으로 지정하고, 정적 파일의 TTL을 86400초(1일)로 설정한다. 파일이 바뀌면 CloudFront 무효화(Invalidation) API를 호출해 엣지 캐시를 즉시 삭제할 수 있다.

## 이 단계에서 중요한 판단 기준

CloudFront 도입 효과를 극대화하려면 TTL 설정이 핵심이다. 자주 바뀌는 HTML은 TTL을 짧게, 바뀌지 않는 해시된 JS·CSS 파일은 TTL을 길게 잡아야 캐시 히트율과 콘텐츠 신선도를 동시에 잡을 수 있다.

## 한 줄 요약 — 이것만 기억하면 된다

**CloudFront는 전 세계 엣지 로케이션에 콘텐츠를 캐시해 사용자와 콘텐츠 사이의 물리적 거리를 줄이는 CDN 서비스로, 정적 자산 배포와 글로벌 서비스 응답 속도 개선에 필수적이다.**

## 나중에 더 깊게 들어가면

- Lambda@Edge / CloudFront Functions: 엣지에서 요청·응답을 가공하는 서버리스 실행 환경
- 서명된 URL / 쿠키: 특정 사용자에게만 콘텐츠 접근을 허용하는 인증 방식
- WAF 연동: CloudFront 앞단에 웹 방화벽을 붙여 DDoS·SQL 인젝션을 차단하는 방법
