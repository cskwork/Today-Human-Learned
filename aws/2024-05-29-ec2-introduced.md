# Amazon EC2 — 물리 서버 없이 가상 서버를 빌리는 방법

> **TL;DR**
> EC2는 AWS에서 빌리는 가상 서버다. 운영체제·CPU·메모리를 선택해 몇 분 안에 실행하고, 필요 없어지면 바로 반납할 수 있다.

---

## EC2를 왜 쓰는지 감 잡기

애플리케이션을 인터넷에 올리려면 어딘가에 서버가 있어야 한다. 직접 서버를 사면 초기 비용이 크고, 트래픽이 몰릴 때를 대비해 평소보다 큰 장비를 미리 사둬야 한다. 트래픽이 없는 시간에도 서버는 계속 전기를 먹는다.

EC2(Elastic Compute Cloud)는 이 문제를 해결한다. Amazon 데이터센터에 있는 물리 서버의 일부를 가상 서버(인스턴스) 형태로 빌려준다. 트래픽이 늘면 인스턴스를 추가하고, 줄면 반납한다. 사용한 시간·자원만큼만 비용을 낸다.

초보자는 처음에 이렇게 이해하면 된다.

`핵심 흐름: AMI 선택 → 인스턴스 타입 결정 → 보안 그룹 설정 → 인스턴스 시작 → 앱 배포`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 인스턴스 (Instance) | 실제로 빌린 가상 서버 한 대. 내 앱이 돌아가는 공간 |
| AMI (Amazon Machine Image) | 인스턴스를 찍어내는 틀. 어떤 OS와 소프트웨어를 깔고 시작할지 정의 |
| 인스턴스 타입 | CPU·메모리·네트워크 성능 조합. t3.micro(소형)부터 x2iedn.32xlarge(초대형)까지 다양 |
| 보안 그룹 (Security Group) | 인스턴스로 들어오고 나가는 트래픽을 제어하는 방화벽 규칙 모음 |
| Auto Scaling | 트래픽 변화에 맞춰 인스턴스 수를 자동으로 늘리거나 줄이는 기능 |

## 예를 들어 설명하면

웹 앱을 EC2에 올리는 전형적인 흐름이다.

```
1. AMI 선택: Amazon Linux 2 + nginx 사전 설치 이미지
2. 인스턴스 타입: t3.micro (개발 환경) → m5.large (운영 환경)
3. 스토리지: EBS 볼륨 30 GB 연결 (앱 데이터 저장)
4. 보안 그룹: 포트 80(HTTP), 443(HTTPS), 22(SSH) 허용
5. 시작 후 SSH로 접속 → 앱 코드 배포
6. Auto Scaling 그룹 설정: CPU 70% 초과 시 인스턴스 자동 추가
7. Elastic Load Balancer: 트래픽을 여러 인스턴스에 분산
```

트래픽 피크가 지나면 Auto Scaling이 불필요한 인스턴스를 자동으로 종료해 비용을 줄인다.

## 이 단계에서 중요한 판단 기준

인스턴스 타입을 고를 때는 "내 앱의 병목이 CPU인가, 메모리인가, 네트워크인가"를 먼저 파악해야 한다. 추측으로 크게 잡는 것보다 작게 시작하고 CloudWatch 지표를 보면서 올리는 것이 비용 면에서 낫다.

## 한 줄 요약 — 이것만 기억하면 된다

**EC2는 AWS에서 가상 서버를 시간 단위로 빌리는 서비스이며, AMI로 환경을 정의하고 Auto Scaling으로 트래픽에 탄력적으로 대응한다.**

## 나중에 더 깊게 들어가면

- EBS vs 인스턴스 스토어: 재시작 후 데이터가 유지되는 방식의 차이
- 스팟 인스턴스: 저렴하지만 AWS가 회수할 수 있는 인스턴스 유형
- VPC 서브넷과 가용 영역: 고가용성 아키텍처를 위한 네트워크 설계
