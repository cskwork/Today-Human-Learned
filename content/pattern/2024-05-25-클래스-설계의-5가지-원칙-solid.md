> **TL;DR**
> SOLID는 클래스를 변경하기 쉽게 만드는 다섯 가지 설계 규칙이다. 각각을 지키면 코드가 뒤엉키지 않는다.

---

## SOLID를 왜 쓰는지 감 잡기

소프트웨어는 처음 만들 때보다 고칠 때 더 많은 시간이 든다. 기능 하나를 바꾸려는데 예상치 못한 곳이 같이 깨지거나, 새 기능을 추가하려면 기존 코드를 전부 뜯어야 하는 상황이 생긴다. SOLID는 이런 상황을 예방하기 위해 로버트 C. 마틴이 정리한 객체지향 설계 원칙 다섯 가지다.

규칙 하나하나가 독립적이지만, 함께 지키면 클래스가 작고 명확한 역할을 갖게 되고, 변경이 한 곳에서만 일어난다.

`핵심 흐름: 클래스 설계 → 단일 책임 → 확장 가능 → 대체 가능 → 인터페이스 분리 → 추상화 의존`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| SRP (단일 책임) | 클래스 하나가 담당하는 일이 딱 하나여야 한다. 이유가 두 개면 클래스를 둘로 나눈다. |
| OCP (개방-폐쇄) | 새 기능은 추가(확장)할 수 있어야 하고, 기존 코드는 건드리지 않아야(폐쇄) 한다. |
| LSP (리스코프 치환) | 자식 클래스는 부모 클래스 자리에 그대로 놓아도 프로그램이 정상 동작해야 한다. |
| ISP (인터페이스 분리) | 쓰지 않는 메서드가 포함된 인터페이스를 억지로 구현하게 하면 안 된다. |
| DIP (의존성 역전) | 구체적인 클래스가 아닌 인터페이스(추상화)에 의존하도록 설계한다. |

## 예를 들어 설명하면

**SRP — 책임을 올바른 곳에 두기**

아래는 `ProductionUpdateService`가 가격 유효성 검증까지 맡고 있는 나쁜 예다.

```java
// 나쁜 예: 서비스가 도메인 규칙(최소 가격)까지 알고 있다
public class ProductionUpdateService {
    public void update(Production production, int price) {
        if (price < 1000) throw new IllegalArgumentException("최소가격은 1000원 이상");
        production.updatePrice(price);
    }
}
```

가격 유효성은 `Production` 자체의 규칙이다. 검증 로직을 `Production.updatePrice()` 안으로 이동하면 서비스는 `updatePrice(price)` 한 줄만 호출하면 된다. 규칙이 바뀌어도 `Production` 하나만 수정한다.

**OCP — 새 타입을 추가할 때 기존 코드를 안 건드리기**

상품 옵션이 늘어날 때마다 `if-else` 블록이 길어지는 대신, `Validator` 인터페이스를 만들고 새 옵션마다 구현체를 추가한다. 기존 `DefaultValidator`, `ETicketValidator`는 그대로 둔다.

**LSP — 치환 가능성 깨뜨리지 않기**

`Square extends Rectangle`에서 `Square`의 `setWidth()`가 높이까지 바꾸면, `Rectangle`로 다루는 코드에서 넓이 계산이 틀린다. 해결책은 상속 대신 공통 인터페이스 `Shape`를 두고, `Rectangle`과 `Square`가 각자 `area()`를 독립 구현하는 것이다.

## 이 단계에서 중요한 판단 기준

클래스를 수정하는 이유가 두 가지 이상이라면 SRP를 위반한 것이고, 새 기능을 추가할 때 기존 클래스에 `if` 블록이 늘어난다면 OCP를 위반한 것이다.

## 한 줄 요약 — 이것만 기억하면 된다

**클래스는 하나의 이유로만 변경되어야 하고, 새 기능은 기존 코드를 건드리지 않고 확장으로 추가해야 한다.**

## 나중에 더 깊게 들어가면

- 의존성 주입(DI) 프레임워크(Spring, Guice)로 DIP를 자동화하는 방법
- 인터페이스 설계 시 어느 수준에서 분리가 적당한지 판단하는 기준
- SOLID가 함수형 프로그래밍 패러다임에서 어떻게 해석되는지
