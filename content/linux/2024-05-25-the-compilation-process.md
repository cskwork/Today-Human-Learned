> **TL;DR**
> 컴파일러는 사람이 쓴 코드를 기계가 이해할 수 있는 형태로 바꾸는 번역 과정이며, 그 첫 단계가 어휘 분석(lexical analysis)이다.

---

## 컴파일을 왜 쓰는지 감 잡기

사람은 `int x = 10;` 같은 코드를 읽지만 CPU는 0과 1의 이진 신호만 이해한다. 이 간격을 메우는 것이 컴파일러다. 컴파일러 없이는 C, Java, Rust 같은 언어로 작성한 코드를 CPU가 직접 실행할 수 없다. 컴파일 과정은 여러 단계로 나뉘어 있고, 각 단계가 앞 단계의 결과물을 입력으로 받아 처리한다.

초보자는 처음에 이렇게 이해하면 된다.

`핵심 흐름: 소스 코드 → 어휘 분석 → 구문 분석 → 코드 생성 → 실행 파일`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 소스 코드 | 개발자가 작성한 사람이 읽을 수 있는 텍스트 형태의 프로그램 |
| 어휘 분석(Lexical Analysis) | 소스 코드를 문자 단위로 읽어 의미 있는 단위(토큰)로 쪼개는 첫 번째 단계 |
| 토큰(Token) | 컴파일러가 인식하는 최소 의미 단위 — 예: 키워드 `int`, 숫자 `10`, 연산자 `=` |
| 렉심(Lexeme) | 소스 코드에서 실제로 잘려 나온 문자열 조각, 토큰의 원재료 |
| 렉서/토크나이저(Lexer/Tokenizer) | 소스 텍스트를 훑으며 렉심을 토큰으로 분류하는 소프트웨어 모듈 |

## 예를 들어 설명하면

`int x = 10;` 한 줄을 컴파일러에 넣으면 렉서는 이렇게 처리한다.

```
int   → 토큰: KEYWORD    렉심: "int"
x     → 토큰: IDENTIFIER  렉심: "x"
=     → 토큰: OPERATOR    렉심: "="
10    → 토큰: NUMBER      렉심: "10"
;     → 토큰: SEMICOLON   렉심: ";"
```

렉서는 문법이나 의미는 아직 신경 쓰지 않는다. "이 문자열이 어떤 종류인가"만 판단한다.

## 이 단계에서 중요한 판단 기준

어휘 분석은 문법을 검사하지 않는다 — 문법 오류는 그다음 단계인 구문 분석(parsing)에서 잡는다.

## 한 줄 요약 — 이것만 기억하면 된다

**컴파일러의 첫 단계인 어휘 분석은 소스 코드를 토큰이라는 최소 단위로 쪼개는 작업이고, 이후 단계들이 그 토큰을 가지고 문법 검사와 코드 생성을 수행한다.**

## 나중에 더 깊게 들어가면

- 구문 분석(Parsing)과 AST(추상 구문 트리) 생성
- 의미 분석(Semantic Analysis) — 타입 검사, 변수 선언 여부 확인
- 중간 코드 생성과 최적화 단계
