> **TL;DR**
> `git pull`은 원격의 최신 변경을 내 로컬에 가져오고, `git push`는 내 변경을 원격으로 보낸다. 이 두 명령이 동기화의 핵심이다.

---

## 동기화를 왜 해야 하는지 감 잡기

팀원이 원격 저장소(GitHub 등)에 코드를 올렸다. 내 로컬에는 그 내용이 없다. 그 상태로 내가 계속 작업하면 나중에 합칠 때 충돌이 커진다. 반대로 내가 로컬에서 작업한 것을 팀원이 볼 수 없으면 협업이 막힌다.

동기화는 이 두 방향의 흐름을 관리하는 일이다. 원격에서 가져오기(pull), 로컬에서 보내기(push), 그 사이에서 충돌 조율(merge).

처음에는 이렇게 이해하면 된다.

`핵심 흐름: fetch(변경 확인) → merge(내 코드에 적용) → push(내 변경 보내기)`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| fetch | 원격의 변경 사항을 내려받되, 내 작업 파일에는 아직 적용하지 않는 명령. 먼저 뭐가 바뀌었는지 확인만 한다. |
| merge | fetch로 가져온 변경을 내 현재 브랜치에 실제로 합치는 작업. |
| pull | fetch + merge를 한 번에 처리하는 단축 명령. 일반적으로 이걸 쓴다. |
| push | 내 로컬 커밋을 원격 저장소로 보내는 명령. 팀원이 볼 수 있게 된다. |
| conflict | 같은 파일의 같은 줄을 나와 팀원이 서로 다르게 수정했을 때 Git이 "직접 선택하라"며 표시해 두는 상태. |

## 예를 들어 설명하면

팀원이 `main` 브랜치에 새 기능을 올렸다. 나도 같은 브랜치에서 다른 파일을 작업 중이다. 동기화 순서는 다음과 같다.

```bash
# 1. 원격 변경 내용만 확인 (내 파일은 아직 그대로)
git fetch origin

# 2. 확인한 내용을 내 브랜치에 적용
git merge origin/main

# 또는 위 두 단계를 한 번에
git pull

# 3. 충돌이 있으면 해당 파일을 열어 수동으로 해결 후 커밋
# 충돌 없이 끝났으면 바로 아래로

# 4. 내 변경 사항을 원격으로 보내기
git push origin main
```

`pull`을 습관적으로 작업 시작 전에 실행하면 충돌 범위가 줄어든다.

## 이 단계에서 중요한 판단 기준

작업 시작 전 반드시 `git pull`로 원격 상태를 가져온다 — 오래 분기된 상태로 작업할수록 나중에 합칠 때 충돌이 커진다.

## 한 줄 요약 — 이것만 기억하면 된다

**`git pull`로 시작하고 `git push`로 마무리하는 것이 팀 협업의 기본 리듬이다.**

## 나중에 더 깊게 들어가면

- `rebase`를 써서 충돌을 더 깔끔하게 처리하는 방법
- `git fetch` 후 `git diff origin/main`으로 변경 사항 미리 검토하기
- 충돌 해결 도구(VS Code, IntelliJ 등)와 3-way merge 이해
