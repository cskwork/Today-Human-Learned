> **TL;DR**
> CORS는 브라우저가 악성 스크립트로부터 사용자를 보호하기 위해 다른 도메인의 리소스 접근을 제한하는 보안 정책이며, 서버가 응답 헤더로 허용 범위를 명시해야 해제된다.

---

## CORS를 왜 쓰는지 감 잡기

웹 브라우저에는 동일 출처 정책(Same-Origin Policy)이라는 기본 보안 규칙이 있다. `a.com`에서 실행 중인 자바스크립트가 `b.com`의 데이터를 마음대로 가져갈 수 있다면, 악성 사이트가 사용자 몰래 은행 계좌나 개인 정보를 빼갈 수 있다. CORS(Cross-Origin Resource Sharing)는 이 규칙을 유지하면서도, 신뢰할 수 있는 출처에 한해 교차 출처 요청을 허용하는 메커니즘이다.

결정권은 클라이언트(브라우저)가 아닌 서버에 있다. 서버가 응답 헤더로 "이 출처는 괜찮다"고 선언해야만 브라우저가 응답 데이터를 자바스크립트에 넘겨준다.

`핵심 흐름: 브라우저 요청 → 서버 응답 헤더 확인 → 허용 출처면 데이터 전달, 아니면 차단`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| `Access-Control-Allow-Origin` | 어떤 출처(도메인)의 요청을 허용할지 지정하는 헤더. `*`이면 전체 허용 |
| `Access-Control-Allow-Methods` | 허용할 HTTP 메서드(GET, POST 등)를 나열하는 헤더 |
| `Access-Control-Allow-Headers` | 요청에 포함할 수 있는 헤더 목록을 지정 |
| Preflight 요청 | 브라우저가 실제 요청 전 OPTIONS 메서드로 서버에 허용 여부를 먼저 묻는 사전 확인 |
| `Access-Control-Max-Age` | Preflight 응답을 캐시할 시간(초). 같은 확인을 반복하지 않아 성능에 도움 |

## 예를 들어 설명하면

프론트엔드가 `https://app.example.com`에서 실행 중이고, API 서버가 `https://api.example.com`에 있는 경우 서버 응답에 아래 헤더가 없으면 브라우저가 요청을 차단한다.

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 3600
```

`Access-Control-Allow-Credentials: true`로 설정하면 쿠키나 인증 토큰을 함께 전송할 수 있다. 단, 이때는 `Allow-Origin`을 `*`로 쓸 수 없고 구체적인 출처를 명시해야 한다.

## 이 단계에서 중요한 판단 기준

CORS 오류가 발생했을 때 브라우저 콘솔 메시지를 먼저 읽어라. "blocked by CORS policy"는 서버 응답 헤더 문제이므로, 해결책은 항상 서버 설정에 있다.

## 한 줄 요약 — 이것만 기억하면 된다

**CORS는 브라우저가 강제하는 보안 정책이고, 서버가 올바른 응답 헤더를 보내야만 교차 출처 요청이 허용된다.**

## 나중에 더 깊게 들어가면

- Preflight 요청의 정확한 발생 조건 (Simple request vs Preflighted request)
- `credentials: 'include'` 옵션과 쿠키 기반 인증 연동
- Nginx·Express·Spring 각 환경에서 CORS 설정하는 구체적 방법
