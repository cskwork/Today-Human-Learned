> **TL;DR**
> 리버스 프록시는 클라이언트 요청을 대신 받아 적절한 백엔드 서버로 전달하고, 그 응답을 클라이언트에게 돌려주는 중간 서버다. 보안·부하 분산·캐싱을 한 곳에서 처리할 수 있다.

---

## 리버스 프록시를 왜 쓰는지 감 잡기

규모 있는 서비스는 웹 서버 하나로 모든 트래픽을 감당하지 않는다. 상품 페이지, 결제, 계정 관리 등 기능별로 서버를 분리한다. 리버스 프록시는 이 구조에서 단일 진입점 역할을 한다. 클라이언트는 리버스 프록시 주소만 알면 되고, 내부 서버가 몇 대인지, 어디에 있는지 알 필요가 없다.

호텔 컨시어지에 비유하면 이해하기 쉽다. 투숙객은 컨시어지에게 요청하고, 컨시어지가 레스토랑·룸서비스·주차 담당에게 각각 연결해준다. 투숙객은 내부 구조를 몰라도 된다.

`핵심 흐름: 클라이언트 → 리버스 프록시 → 적합한 백엔드 서버 → 리버스 프록시 → 클라이언트`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 리버스 프록시 | 클라이언트 앞이 아닌 서버 앞에 서는 대리인. 클라이언트 요청을 받아 내부 서버로 전달 |
| 로드 밸런싱 | 들어오는 요청을 여러 서버에 고르게 나눠 특정 서버가 과부하되지 않도록 분산 |
| SSL 종료(SSL Termination) | HTTPS 암호화를 리버스 프록시에서 해제하고 내부 통신은 HTTP로 처리하는 방식 |
| 캐싱 | 자주 요청되는 응답을 리버스 프록시가 저장해두고 백엔드 서버 없이 직접 돌려주는 기능 |
| 익명화 | 백엔드 서버의 IP와 내부 구조를 클라이언트에게 노출하지 않아 공격 표면을 줄임 |

## 예를 들어 설명하면

이커머스 사이트에 3개의 서버가 있다고 가정한다.

```
사용자 요청: GET /products/123

리버스 프록시가 판단:
  /products/* → 상품 서버 (192.168.1.10)
  /checkout/* → 결제 서버 (192.168.1.20)
  /account/*  → 계정 서버 (192.168.1.30)

1. 리버스 프록시가 상품 서버로 요청 전달
2. 상품 서버가 응답 생성
3. 리버스 프록시가 동일한 상품 페이지를 캐시에 저장
4. 이후 같은 요청은 캐시에서 직접 응답 (상품 서버 부하 없음)
```

## 이 단계에서 중요한 판단 기준

리버스 프록시를 쓸지 결정할 때 핵심 질문은 하나다. "외부에 노출할 서버가 2개 이상이거나, 보안·성능 제어가 한 곳에 집중되어야 하는가?" 그렇다면 리버스 프록시를 도입하는 것이 맞다.

## 한 줄 요약 — 이것만 기억하면 된다

**리버스 프록시는 클라이언트에게는 서버처럼, 서버에게는 클라이언트처럼 보이는 중간 레이어로 보안·분산·캐싱을 한 번에 처리한다.**

## 나중에 더 깊게 들어가면
