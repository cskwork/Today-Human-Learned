> **TL;DR**
> 계층형 아키텍쳐는 DB가 모든 것을 지배하게 되는 구조적 함정이 있다. 클린 아키텍쳐(육각형 아키텍쳐)는 의존성 방향을 뒤집어 도메인 로직이 중심이 되도록 만든다.

---

## 클린 아키텍쳐를 왜 쓰는지 감 잡기

전통적인 계층형 아키텍쳐(웹 계층 → 서비스 계층 → 영속성 계층)는 직관적이지만 치명적인 문제가 있다. 영속성 계층이 맨 아래에 있기 때문에 모든 계층이 결국 DB 구조에 종속된다. 시간이 지나면 서비스 로직이 웹 계층으로 흘러들어가고, 단위 테스트를 쓰려면 DB 모킹이 필수가 되며, 여러 개발자가 같은 기능을 동시에 작업하기 어려워진다. 클린 아키텍쳐는 의존성의 방향을 바꿔서 도메인(비즈니스 규칙)이 DB와 웹 프레임워크 어디에도 종속되지 않게 만든다.

초보자는 처음에 이렇게 이해하면 된다.

`외부 요청(어댑터) → 포트(인터페이스) → 유스케이스(서비스) → 도메인 엔티티`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 도메인 엔티티 | 비즈니스 규칙 그 자체. Account, Order 같은 핵심 객체로, DB나 프레임워크를 전혀 모른다. |
| 유스케이스 | "계좌 이체" 같은 하나의 사용자 시나리오를 처리하는 서비스 로직. 도메인 엔티티를 조합해 일을 처리한다. |
| 포트(Port) | 유스케이스가 외부와 대화하는 인터페이스. 인바운드 포트(들어오는 요청)와 아웃바운드 포트(DB 호출 등 나가는 요청)로 나뉜다. |
| 어댑터(Adapter) | 포트의 실제 구현체. 웹 컨트롤러(인바운드)나 JPA 리포지토리 구현(아웃바운드)이 여기에 해당한다. |
| 의존성 역전 원칙 | 상위 모듈(도메인)이 하위 모듈(DB)에 직접 의존하지 않고, 둘 다 추상(인터페이스)에 의존하게 만드는 원칙. |

## 예를 들어 설명하면

아키텍쳐적으로 표현력 있는 패키지 구조는 아래와 같다.

```
payment
  account
    adapter
      in/web         <- AccountController (HTTP 요청 수신)
      out/persistence <- AccountPersistenceAdapter (DB 접근)
    domain           <- Account, Activity (순수 도메인 객체)
    application
      SendMoneyService  <- 유스케이스 구현
      port
        in  <- SendMoneyUseCase (인바운드 포트 인터페이스)
        out <- LoadAccountPort, UpdateAccountStatePort (아웃바운드 포트 인터페이스)
```

핵심은 `SendMoneyService`가 `AccountPersistenceAdapter`를 직접 호출하지 않는다는 점이다. 서비스는 `LoadAccountPort` 인터페이스에만 의존하고, 어댑터가 그 인터페이스를 구현한다. 덕분에 DB를 교체해도 서비스 코드는 건드릴 필요가 없다.

## 이 단계에서 중요한 판단 기준

도메인 로직을 수정할 때 DB 설정 파일이나 JPA 어노테이션을 건드려야 한다면, 의존성 방향이 잘못된 것이다.

## 한 줄 요약 — 이것만 기억하면 된다

**클린 아키텍쳐의 핵심은 의존성의 방향 — 모든 화살표가 도메인 엔티티를 향해야 하며, 도메인은 DB와 프레임워크를 전혀 알 필요가 없어야 한다.**

## 나중에 더 깊게 들어가면

- 인바운드 포트와 아웃바운드 포트를 각각 좁게 유지하는 인터페이스 분리 원칙(ISP) 적용법
- 유스케이스 단위 테스트에서 어댑터를 목(Mock)으로 교체하는 구체적인 방법
- 스프링 부트에서 `@UseCase`, `@WebAdapter`, `@PersistenceAdapter` 커스텀 어노테이션으로 역할을 명시하는 패턴
