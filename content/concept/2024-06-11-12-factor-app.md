> **TL;DR**
> 12 Factor App은 "어디서든 배포하고, 어디서든 동작하는" 앱을 만들기 위한 12개의 실천 원칙이다. 클라우드 환경에서 수년간 쌓인 경험을 규칙으로 정리한 것이다.

---

## 12 Factor App을 왜 쓰는지 감 잡기

개발 환경에서는 잘 돌아가던 앱이 운영 서버에 올리면 문제가 생기는 경우가 많다. 환경 변수가 다르거나, 의존성 버전이 충돌하거나, 로그를 어디서 봐야 할지 모르는 상황이 대표적이다.

12 Factor App은 Heroku 팀이 2011년에 정리한 방법론이다. 웹 앱을 개발하고 운영하면서 반복적으로 겪는 문제들을 예방하는 12개의 원칙을 담고 있다. 이 원칙을 지키면 앱이 클라우드 플랫폼 어디서든 일관되게 동작하고, 팀 규모가 커져도 관리하기 쉬워진다.

초보자는 이렇게 이해하면 된다.

`핵심 흐름: 코드 작성 → 선언적 설정 → 환경과 분리 → 스테이트리스 프로세스 → 어디서든 배포`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| Codebase | 하나의 앱 = 하나의 저장소. Git 한 개에서 여러 환경(운영, 개발)으로 배포한다. |
| Config (환경 변수) | DB 주소, API 키 같은 설정값은 코드 밖 환경 변수에 저장한다. 코드에 하드코딩하지 않는다. |
| Backing Service | DB, 캐시, 메시지 큐 같은 외부 서비스. 코드 수정 없이 교체할 수 있어야 한다. |
| Stateless Process | 각 프로세스는 상태를 메모리에 저장하지 않는다. 상태는 DB나 캐시 같은 외부 저장소에 둔다. |
| Dev/Prod Parity | 개발 환경과 운영 환경의 차이를 최소화한다. "내 컴퓨터에선 됐는데"를 없앤다. |

## 예를 들어 설명하면

사진 공유 앱을 12 Factor 방식으로 만든다고 가정한다.

```bash
# Factor 3: Config — 설정을 환경 변수로 분리
export DATABASE_URL="postgres://user:pass@prod-db:5432/myapp"
export AWS_S3_BUCKET="my-photo-bucket"

# Factor 2: Dependencies — 의존성 명시적 선언
# package.json 또는 requirements.txt에 버전 고정
# npm ci 또는 pip install -r requirements.txt로 정확히 설치

# Factor 11: Logs — 표준 출력으로만 로그 내보내기
# 파일로 직접 쓰지 않고 stdout에 출력하면
# CloudWatch, ELK 같은 외부 서비스가 수집한다
console.log(JSON.stringify({ level: "info", event: "photo_uploaded", userId: 42 }))
```

12개 원칙 중 Config, Dependencies, Logs 이 세 가지만 지켜도 운영 사고의 절반은 줄어든다.

## 이 단계에서 중요한 판단 기준

"코드를 바꾸지 않고 환경만 바꿔서 다른 서버에 배포할 수 있는가를 항상 확인한다."

## 한 줄 요약 — 이것만 기억하면 된다

**설정은 환경 변수로, 상태는 외부 저장소로, 로그는 표준 출력으로 — 이 세 가지가 12 Factor의 핵심이다.**

## 나중에 더 깊게 들어가면

- 12 Factor 원칙을 Kubernetes 환경에 적용하는 방법 (ConfigMap, Secret)
- Factor 6 프로세스 모델과 수평 확장 설계
- 12 Factor를 넘어선 Beyond 12 Factor (보안, 텔레메트리 추가 원칙)
