> **TL;DR**
> 시스템 설계란 "이 소프트웨어가 많은 사람이 쓰고 장애가 나도 버티게 하려면 어떻게 구조를 짤 것인가"를 결정하는 일이며, 요구사항 파악에서 시작해 트레이드오프를 따지는 반복 과정이다.

---

## 시스템 설계를 왜 하는지 감 잡기

코드를 잘 짜는 것과 시스템을 잘 설계하는 것은 다른 일이다. 함수 하나는 잘 돌아가도, 100만 명이 동시에 접속하면 서버가 다운되거나 응답이 느려진다. 시스템 설계는 이런 문제를 미리 구조적으로 막는 작업이다.

현실에서는 세 가지 문제가 자주 등장한다. 첫째, 사용자가 100명에서 100만 명으로 늘었을 때 어떻게 감당할 것인가(확장성). 둘째, 서버 하드웨어가 갑자기 죽어도 서비스가 계속 돌아가게 할 것인가(가용성). 셋째, 전 세계 어디서 접속해도 응답이 200ms 안에 오게 할 것인가(성능).

`핵심 흐름: 요구사항 파악 → 규모 추정 → 구성 요소 설계 → 병목 해결 → 반복 개선`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 확장성 (Scalability) | 사용자나 데이터가 늘어나도 성능이 유지되는 능력 |
| 로드 밸런서 (Load Balancer) | 들어오는 요청을 여러 서버에 골고루 나눠주는 중계 장치 |
| 캐시 (Cache) | 자주 쓰는 데이터를 빠른 저장소에 미리 올려두어 DB 호출을 줄이는 기법 |
| 마이크로서비스 | 하나의 큰 앱을 기능별 작은 서비스로 쪼개 독립적으로 배포하는 아키텍처 |
| CAP 정리 | 분산 시스템에서 일관성·가용성·분단 내성 세 가지를 동시에 모두 만족시킬 수 없다는 원칙 |

## 예를 들어 설명하면

URL 단축 서비스(TinyURL)를 설계한다고 가정한다.

```
클라이언트
    |
[API Gateway]  ← 인증, 속도 제한
    |
[단축 서비스]  ← 고유 ID 생성, DB에 URL 저장
    |
[캐시(Redis)]  ← 자주 쓰이는 단축 URL → 원본 URL 매핑 보관
    |
[DB(MySQL)]    ← 영구 저장
```

읽기가 쓰기보다 훨씬 많으므로 캐시가 DB 부하를 대부분 흡수한다. 단축 ID는 Base62 인코딩으로 생성해 충돌을 줄인다. 이 구조 하나만 익혀도 비슷한 설계 문제의 70%를 커버할 수 있다.

## 이 단계에서 중요한 판단 기준

설계를 시작하기 전에 "지금 실제로 이 문제가 있는가, 아니면 있을 것 같아서 미리 복잡하게 만드는 것인가"를 먼저 물어봐라 — YAGNI(You Aren't Gonna Need It) 원칙이 과잉 설계를 막는다.

## 한 줄 요약 — 이것만 기억하면 된다

**좋은 시스템 설계는 완벽한 구조를 한 번에 내놓는 것이 아니라, 현재 요구사항에 맞게 단순하게 시작하고 트레이드오프를 인식하면서 점진적으로 개선하는 과정이다.**
