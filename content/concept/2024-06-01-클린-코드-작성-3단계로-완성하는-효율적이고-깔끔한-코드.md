> **TL;DR**
> 코드를 한 번에 완벽하게 짜려 하지 말고, 동작 확인 → 테스트 검증 → 리팩토링 순서를 지키면 유지보수 가능한 코드가 만들어진다.

---

## 클린 코드 3단계를 왜 쓰는지 감 잡기

"일단 돌아가게만 만들자"는 접근은 단기적으로 빠르지만, 몇 달 뒤 코드를 수정할 때 어디를 건드려야 할지 알 수 없는 상태가 된다. 기능이 복잡하게 얽히면 버그 하나를 고치다 다른 곳이 터진다. 이 문제를 해결하기 위해 "Make It Work → Make It Right → Clean It Up"이라는 순서가 제안됐다. 단계를 나누면 한 번에 생각해야 할 것이 줄어들고, 각 단계마다 명확한 완료 기준이 생긴다.

초보자는 처음에 이렇게 이해하면 된다.

`핵심 흐름: 기능 구현(Work) → 테스트로 검증(Right) → 구조 개선(Clean)`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| Make It Work | 완벽하지 않아도 목표 기능이 동작하도록 먼저 코드를 작성하는 단계 |
| Make It Right | 테스트를 작성해 정상 케이스와 예외 케이스 모두 통과하는지 확인하는 단계 |
| Make It Clean | 동작이 확인된 코드를 읽기 좋고 중복 없이 정리하는 단계 |
| 엣지 케이스 | 빈 입력, 최댓값 초과처럼 예상에서 벗어난 경계 조건 |
| 리팩토링 | 외부 동작은 바꾸지 않고 코드 내부 구조만 개선하는 작업 |

## 예를 들어 설명하면

로그인 기능을 구현한다고 가정한다.

1. **Make It Work**: 아이디·비밀번호를 받아 DB에서 조회하고, 일치하면 세션을 생성하는 코드를 작성한다. 변수 이름이 `pw`여도 괜찮다.
2. **Make It Right**: 테스트를 작성한다.
   - 정상 아이디/비밀번호 → 로그인 성공
   - 틀린 비밀번호 → 실패 응답 반환
   - 빈 값 입력 → 유효성 오류 반환
3. **Make It Clean**: 테스트가 모두 통과한 상태에서 `pw`를 `userPassword`로 바꾸고, 중복된 DB 조회 로직을 별도 함수로 추출한다. 리팩토링 중간마다 테스트를 다시 실행해 동작이 유지되는지 확인한다.

## 이 단계에서 중요한 판단 기준

테스트 없이 Clean 단계로 넘어가지 않는다. 안전망이 없는 리팩토링은 동작을 깨뜨려도 즉시 알아채지 못한다.

## 한 줄 요약 — 이것만 기억하면 된다

**동작 → 검증 → 정리 순서를 지키면, 리팩토링이 두려운 게 아니라 자연스러운 마지막 단계가 된다.**

## 나중에 더 깊게 들어가면

- TDD(테스트 주도 개발): Make It Right를 먼저 쓰고 Work를 나중에 하는 역순 접근법
- 뮤테이션 테스팅: 테스트 코드 자체의 품질을 검증하는 기법
- 기술 부채 관리: Clean 단계를 언제, 얼마나 자주 가져가야 하는지 팀 단위 전략
