> **TL;DR**
> - 글로벌 설정은 두 파일에 산다: `~/.claude/CLAUDE.md`(시스템 프롬프트) + `~/.claude/settings.json`(권한).
> - **한 태스크 끝나면 `/clear`** — 컨텍스트가 쌓이면 환각 확률이 급격히 올라간다.
> - Claude 4.6+에서 **`claude-mem` 같은 외부 메모리 플러그인은 더 필요 없다.** 내장 메모리로 대체됨.
> - "도박처럼 확률적이고, 단기기억상실이며, 능력은 천재급" — 이 비유 하나가 운영 규칙 대부분의 근거다.

---

## 1. 두 개의 설정 파일만 기억하면 된다

Claude Code의 글로벌 동작은 두 파일이 결정한다.

| 파일 | 역할 | macOS / Linux | Windows |
|---|---|---|---|
| `CLAUDE.md` | 모든 프로젝트에 적용되는 시스템 프롬프트 | `~/.claude/CLAUDE.md` | `%USERPROFILE%\.claude\CLAUDE.md` |
| `settings.json` | 권한 (자동 허용/거부 명령) 및 hook 설정 | `~/.claude/settings.json` | 동일 |

**프로젝트별 오버라이드**는 해당 프로젝트 디렉터리에 `CLAUDE.md`를 두면 자동 로드된다. 같은 파일명을 쓰지만 글로벌이 먼저 로드되고 프로젝트가 덧붙는 구조.

`settings.json`의 권한 패턴은 "이 도구는 묻지 말고 실행해라" 또는 "절대 실행하지 마라"를 미리 박아두는 용도. 매 명령마다 묻는 걸 줄이려면 자주 쓰는 안전한 명령(예: `Bash(git status)`, `Bash(ls)`)을 allow에 추가한다.

## 2. 한 태스크 끝나면 무조건 `/clear`

가장 중요한 규칙. 같은 세션에서 여러 무관한 작업을 이어 하면 **이전 시도의 실패 흔적이 현재 시도의 사고에 섞여 들어간다.**

```text
[작업 A 시도] → 실패 → 다른 접근으로 성공
[작업 B 시도] → 모델이 A의 실패 메모리에서 "이건 안 되는 패턴이야" 같은 잘못된 일반화를 함
```

`/clear`는 그 시점까지의 대화 컨텍스트를 비운다. 메모리/설정 파일은 그대로 살아 있다.

판단 기준:
- 한 PR / 한 이슈 작업 끝 → `/clear`
- "에러 → 시도 → 실패 → 다른 시도" 가 3회 이상 누적 → `/clear` 후 재시작
- 컨텍스트 사용량이 40% 넘어가는데 본 작업이 아직 시작도 안 됐다 → `/clear`

auto-compact를 켜두면 자동으로 압축이 일어나긴 하지만, **압축 ≠ 청소**. 압축은 요약을 남기고, 그 요약 자체가 다음 작업의 잡음이 된다. 단일 태스크 후 청소가 정공법.

## 3. Claude 4.6+ 이후 "사라진" 도구들

생태계가 빠르게 바뀐다. 2026년 초 기준 더 이상 권장되지 않는 도구:

- **외부 메모리 플러그인** (claude-mem 등) — Claude 내장 메모리(`<remember>` 태그, 자동 컨텍스트 매니지먼트)로 대체.
- **수동 컨텍스트 관리 매크로** — auto-compact가 기본 켜짐.

지금도 권장되는 것:
- **상태값 플러그인** (claude-dashboard 류) — 현재 모델, 컨텍스트 사용량, 브랜치, 비용을 한눈에. 상태를 모르고 작업하면 비용/컨텍스트 사고가 난다.
- **LSP** — 언어별 정의 점프/리네임을 도구가 처리. grep보다 정확.
- **Code simplifier** — 변경 후 "이거 더 줄일 수 있나?" 패스를 자동화.

## 4. 작업 시작 전 `/init` 한 번

처음 들어가는 프로젝트는 무조건 `/init`. 이 명령은 프로젝트 디렉터리를 스캔해서 **프로젝트 구조 요약을 `CLAUDE.md`에 만들어준다.** 이후 모든 세션이 이 요약을 기본 컨텍스트로 들고 들어간다.

`/init` 없이 작업하면 모델이 매번 디렉터리 구조부터 다시 탐색해서 토큰을 태운다. 한 번 만들고 잊으면 끝.

## 5. 멀티 에이전트 — Vibe Kanban / Symphony 류

병렬로 여러 에이전트를 돌리고 싶을 때.

- **Vibe Kanban** 같은 데스크탑 앱: IDE 연동 + Claude Code / Codex / OpenCode 등 여러 에이전트를 칸반 보드 위에 늘어놓고 병렬 작업.
- **장점**: 독립적인 작업(예: "리팩토링" + "테스트 작성" + "문서화")을 동시에 진행. 각 에이전트는 격리된 컨텍스트.
- **단점**: 작업 간 의존성이 있으면 충돌. 머지 시점에 사람이 정리해야 함.

판단 기준은 **"이 작업들이 서로 결과를 보지 않고도 끝낼 수 있나?"** 그렇다면 병렬. 아니면 순차.

## 6. 코드 리뷰는 다른 모델로

같은 모델이 자기 작업을 리뷰하면 같은 사각지대를 갖는다. 검증된 패턴:

- Claude Opus가 구현 → **Codex(high reasoning)** 또는 **GPT 추론 모델**이 리뷰.
- 반대도 가능: Codex 구현 → Claude가 리뷰.

서로 다른 학습 분포·다른 강점이 사각지대를 줄인다. **"두 모델이 모두 OK라고 한 코드"는 "한 모델이 OK라고 한 코드"보다 훨씬 안전하다.**

CLI에서 직접 다른 모델로 리뷰를 트리거하는 OSS 도구도 늘어나고 있다 (Claude-Codex-Gemini 트리오 같은 식).

## 7. CLAUDE.md 작성의 핵심 4원칙

내가 쓰는 글로벌 CLAUDE.md의 뼈대 4가지. 이 4개가 모델 행동 대부분을 결정한다.

### 7-1. 코딩 전에 먼저 생각하라

> 추측하지 말고, 헷갈리는 점을 숨기지 말고, 트레이드오프를 드러내라.

- 가정을 명시한다. 확실하지 않으면 묻는다.
- 해석이 여러 개면 다 제시한다 — 조용히 하나 고르지 않는다.
- 더 단순한 접근이 있으면 말한다. 필요하면 반대 의견을 낸다.
- 불명확하면 **멈춘다.** 뭐가 헷갈리는지 짚고 묻는다.

LLM은 자신감 있게 틀린 답을 쏟아낼 수 있다. "확신 없을 땐 묻기"를 시스템 프롬프트로 강제하지 않으면 절대 자기가 먼저 묻지 않는다.

### 7-2. 단순함 우선

> 문제를 해결하는 데 필요한 최소한의 코드만 작성하라.

- 요청받지 않은 기능을 넣지 마라.
- 한 번 쓸 코드에 추상화 도입 금지.
- "유연성", "설정 가능성"을 요청 없이 추가 금지.
- 발생할 수 없는 상황에 대한 에러 처리 금지.
- **200줄 썼는데 50줄로 풀린다면 다시 써라.**

체크 질문: *"시니어 엔지니어가 이걸 보고 과하다고 할까?"* — 그렇다면 줄여라.

### 7-3. 수술하듯 필요한 부분만 수정

> 정말 필요한 부분만 건드려라. 정리는 네가 만든 흔적만 하라.

- 주변 코드, 주석, 포맷까지 "개선"하지 마라.
- 안 망가진 걸 리팩토링하지 마라.
- 네 스타일이 달라도 기존 스타일에 맞춰라.
- 관련 없는 죽은 코드는 **언급만** 하라. 삭제 X.

기준은 한 문장: **변경된 모든 줄은 사용자 요청과 직접 연결돼야 한다.**

### 7-4. 목표 중심으로 실행

> 성공 기준을 정의하고, 검증될 때까지 반복하라.

작업을 검증 가능한 목표로 변환:
- "검증 추가" → "잘못된 입력 테스트를 작성하고 그게 통과하게 만든다"
- "버그 수정" → "버그를 재현하는 테스트 작성 → 통과하게 수정"
- "X 리팩토링" → "전후 모두 테스트 통과 확인"

여러 단계라면 짧은 계획을 미리 제시:
```text
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

강한 성공 기준이 있으면 모델이 스스로 반복하며 진행한다. 약한 기준("되게 만들어라")은 계속 사람의 확인이 필요해진다.

## 8. 운영 비유 — 왜 이런 규칙들이 필요한가

LLM 에이전트는 세 단어로 요약된다:

- **도박** — 같은 프롬프트에 같은 답을 보장하지 않는다. 확률적이다.
- **단기기억상실** — 세션이 끝나면 잊는다. 컨텍스트 안에서도 길어지면 앞을 흐릿하게 본다.
- **천재 사원** — 능력 자체는 시니어급. 하지만 위 두 한계 때문에 매번 새 신입처럼 가이드해줘야 함.

위 가이드라인들은 모두 이 세 한계를 보완하는 장치다.
- `/clear` = 단기기억상실의 부작용 차단
- `CLAUDE.md` = 매번 잊어버리는 천재에게 회사 룰을 처음부터 다시 깔아주는 것
- 다른 모델 리뷰 = 도박의 분산 줄이기
- 명시적 성공 기준 = 천재가 자기 검증 가능하도록

이 비유를 손에 쥐고 시작하면 새로운 도구/플러그인이 나와도 "내가 어떤 한계를 보완하는 거지?" 로 판단할 수 있다.

## 9. 추천 학습 경로

1. **첫 주**: CLAUDE.md + settings.json 한 번 세팅, `/init` + `/clear` 만 익히기. 다른 거 다 무시.
2. **둘째 주**: 자주 막히는 패턴 하나를 CLAUDE.md에 1줄로 박기. 작업 끝날 때마다 회고로 1줄씩 늘리기.
3. **셋째 주**: 멀티 에이전트(Vibe Kanban 등) 시도. 단, 독립 작업에만.
4. **넷째 주**: 다른 모델로 코드 리뷰 도입. 차이 나는 지점 관찰.

한꺼번에 다 도입하지 마라 — 도구가 늘면 운영 부담이 늘고, **운영 부담을 못 따라가면 도구 자체가 사고 원인이 된다.**
