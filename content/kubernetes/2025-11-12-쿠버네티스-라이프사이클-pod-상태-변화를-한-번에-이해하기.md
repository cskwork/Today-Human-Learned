> **TL;DR**
> Pod 라이프사이클은 Phase(큰 그림) → Condition(서비스 가능 여부) → Container State(세부 상태) 세 층으로 구성되며, 이 순서로 보면 장애 원인을 빠르게 찾을 수 있다.

---

## Pod 라이프사이클을 왜 알아야 하는지 감 잡기

`kubectl get pods`를 실행했을 때 STATUS 컬럼에 `CrashLoopBackOff`, `ImagePullBackOff`, `Terminating`이 뜨면 어디서부터 봐야 할지 막막하다. 이 메시지들은 사실 "라이프사이클"이라는 하나의 흐름 안에서 벌어지는 단계별 사건들이다.

흐름을 이해하면 세 가지가 명확해진다. 어디서 멈춘 건지, 언제 트래픽을 받기 시작했는지, 종료 신호를 보낸 뒤 얼마나 기다려야 하는지. 오토스케일링, 롤링 업데이트, 헬스체크, graceful shutdown 같은 운영 기능도 모두 이 라이프사이클 위에서 동작한다.

`핵심 흐름: 스케줄링 → 이미지 풀 → Init 컨테이너 → 메인 컨테이너 → Readiness 통과 → 서비스 트래픽 → 종료 신호 → Grace Period → 삭제`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| Pod Phase | Pod 전체의 거친 상태 요약. Pending / Running / Succeeded / Failed / Unknown 다섯 가지 |
| Pod Condition | "이 Pod가 트래픽을 받을 준비가 됐는가"를 나타내는 플래그 모음. Ready가 핵심 |
| Container State | 개별 컨테이너의 세부 상태. Waiting / Running / Terminated |
| Lifecycle Hook | 컨테이너 시작 직후(postStart)와 종료 직전(preStop)에 실행하는 사용자 정의 명령 |
| Grace Period | 종료 신호(SIGTERM) 후 강제 종료(SIGKILL) 전까지 기다리는 시간. 기본 30초 |

## 예를 들어 설명하면

Pod가 시작할 때와 종료될 때의 흐름이다.

**시작 흐름:**
```
kubectl apply  →  스케줄러가 노드 선택  →  kubelet이 이미지 풀
  →  Init 컨테이너  →  메인 컨테이너  →  Readiness Probe 성공
  →  Ready=True  →  서비스 로드밸런싱 풀에 포함
```

**종료 흐름:**
```
kubectl delete  →  Endpoints에서 Pod 제거 (트래픽 차단)
  →  preStop hook 실행  →  SIGTERM 전송
  →  terminationGracePeriodSeconds 대기  →  SIGKILL (타임아웃 시)
  →  etcd에서 Pod 정보 삭제
```

`CrashLoopBackOff`는 Phase가 아니라 컨테이너가 반복적으로 실패할 때 kubelet이 재시작 간격을 늘리며 표시하는 세부 Reason이다. Phase는 여전히 Running일 수 있다.

## 이 단계에서 중요한 판단 기준

STATUS 한 줄만 보지 말고, `kubectl describe pod <이름>`으로 Conditions 변화 시간과 Events 섹션을 함께 봐야 실제 원인(이미지 풀 실패, 프로브 실패, hook 오류 등)이 드러난다.

## 한 줄 요약 — 이것만 기억하면 된다

**STATUS는 겉표지일 뿐이고, Phase → Condition → Container State 순서로 좁혀가야 진짜 장애 원인이 보인다.**

## 나중에 더 깊게 들어가면

- Readiness / Liveness / Startup Probe의 파라미터 튜닝 (failureThreshold, initialDelaySeconds)
- preStop hook 설계 원칙 (Grace Period보다 짧게, 멱등하게)
- Job·CronJob의 `backoffLimit`과 `restartPolicy` 전략
