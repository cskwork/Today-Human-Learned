> **TL;DR**
> Redis에는 테이블 스키마가 없으므로, 키 네이밍 규칙과 자료구조·필드·TTL을 명세서로 문서화해야 협업과 유지보수가 가능해진다.

---

## Redis 스키마 문서화를 왜 해야 하는지 감 잡기

관계형 DB는 `CREATE TABLE`로 구조가 코드에 박혀 있다. Redis는 그런 강제가 없다. 개발자마다 키를 다르게 만들면 `user:1`, `users:1`, `u:1`이 공존하는 혼돈이 생긴다. 더 심각한 건, 어떤 필드가 Hash에 들어있는지, TTL이 걸려있는지 코드를 뒤져야 안다는 점이다. 명세서 한 장이 이 혼돈을 막는다.

초보자는 처음에 이렇게 이해하면 된다.

`핵심 흐름: 키 패턴 정의 → 자료구조 선택 → 필드 목록 기술 → TTL·인덱스 키 명시`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| Key Prefix | 키 이름의 앞부분 패턴. `user:{userId}` 형태로 도메인과 ID를 결합한다. |
| TTL | 키에 설정하는 만료 시간. 캐시 용도라면 반드시 설정한다. |
| Secondary Key (인덱스 키) | 목록 조회를 위해 ID만 모아두는 별도 Set 키. 예: `user:all` |
| Hash Field | Hash 자료구조 안의 개별 속성. RDBMS의 컬럼에 해당한다. |
| Access Pattern | 데이터를 어떻게 읽고 쓰는지의 패턴. 자료구조 선택의 기준이 된다. |

## 예를 들어 설명하면

사용자 도메인의 명세서 예시다.

| 항목 | 내용 |
|---|---|
| Key Prefix | `user:{userId}` |
| Data Structure | Hash |
| Fields | name (String), age (Integer), email (String), joined_at (Timestamp) |
| TTL | 없음 |
| Index Key | `user:all` (Set) — 전체 userId 목록 |
| 주의사항 | email 유니크 보장이 필요하면 별도 인덱스 Set 추가 |

실제 명령어로 표현하면:

```
HSET user:1001 name "Alice" age 30 email "alice@example.com" joined_at 1672531200
SADD user:all 1001

# 전체 사용자 목록 조회
SMEMBERS user:all
# 특정 사용자 조회
HGETALL user:1001
```

## 이 단계에서 중요한 판단 기준

자료구조 선택은 "어떻게 조회할 것인가"로 결정한다 — 단순 키-값 조회면 String, 부분 필드 수정이 필요하면 Hash, 정렬이 필요하면 Sorted Set을 선택한다.

## 한 줄 요약 — 이것만 기억하면 된다

**Redis 명세서는 키 패턴, 자료구조, 필드, TTL, 인덱스 키 다섯 가지를 문서로 정해두는 것이다.**

## 나중에 더 깊게 들어가면

- 멀티키 원자 연산이 필요할 때 Lua 스크립트 활용
- 메모리 절약을 위한 Hash vs. 직렬화된 JSON String 선택 기준
- Redis 7의 키 공간 알림(Keyspace Notifications)으로 TTL 만료 감지
