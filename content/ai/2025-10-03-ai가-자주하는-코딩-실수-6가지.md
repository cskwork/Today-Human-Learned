> **TL;DR**
> AI가 생성한 코드는 기능은 동작해도 팀 패턴을 무시하고, 타입을 중복 정의하고, 에러 처리를 생략하는 구조적 결함을 자주 갖는다.

---

## 왜 이 문제가 생기는지 감 잡기

AI는 기본적으로 "해피 패스 최적화" 전략을 쓴다. 요청된 기능이 동작하면 완료로 판단하기 때문에, 팀 규칙이나 실패 경로는 프롬프트에 명시하지 않으면 고려하지 않는다. 신입 개발자는 결과물이 돌아가는 것을 보고 통과시키기 쉬워 더 취약하다. 아래 6가지 패턴을 사전에 인식하면 "돌아가는 코드"를 "유지보수 가능한 코드"로 바꿀 수 있다.

초보자는 이렇게 이해하면 된다.

`핵심 흐름: AI 코드 생성 → 기능 동작 확인 → 구조 문제 점검 (6가지) → 수정`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| One Source of Truth | 타입이나 상수가 코드베이스 전체에 딱 한 곳에만 정의되는 원칙 — 여러 곳에 흩어지면 하나 바꿀 때 나머지가 깨진다 |
| 매직 값 (Magic Value) | 코드 중간에 박힌 `"완료"`, `30000` 같은 날것의 숫자나 문자열 — 의미를 알 수 없어 변경이 위험하다 |
| SRP (단일 책임 원칙) | 한 파일/함수는 한 가지 일만 해야 한다는 규칙 — UI, 비즈니스 로직, API 호출이 한 곳에 뒤섞이면 위반이다 |
| 타입 가드 (Type Guard) | `unknown` 타입을 구체적인 타입으로 좁히는 TypeScript 패턴 — `any` 대신 써야 한다 |
| Shared 모듈 | 두 곳 이상에서 재사용하고 도메인에 독립적인 유틸·훅·상수를 모아둔 공용 폴더 |

## 예를 들어 설명하면

타입 중복 정의는 가장 흔한 실수다. 같은 `Product` 타입이 페이지마다 미묘하게 다르게 정의되면 필드 하나를 바꿀 때 전체가 무너진다.

```typescript
// 나쁜 예: 두 파일에 각각 정의
// page A
type Product = { id: string; status: "CANCEL" | "DONE" }
// page B
type Product = { id: string; status: "CANCELLED" | "DONE" } // 철자가 다름

// 좋은 예: 한 파일에서 정의하고 import만 사용
// src/modules/product/types.ts
export interface Product {
  id: string;
  status: ProductStatus;
}
export enum ProductStatus {
  CANCELLED = "CANCELLED",
  DONE = "DONE",
}
```

에러 처리도 마찬가지다. `console.error`로 덮는 대신 사용자 메시지와 구조화된 로깅을 함께 제공해야 한다.

```typescript
async function submit(order: Order) {
  try {
    await api.orders.create(order);
    toast("주문이 완료됐어요.");
  } catch (e: unknown) {
    log.error("createOrder failed", { e, orderId: order.id });
    toast("주문 중 문제가 발생했어요. 잠시 뒤 다시 시도해주세요.");
  }
}
```

## 이 단계에서 중요한 판단 기준

코드 리뷰 전에 "이 파일에 UI, 비즈니스 로직, IO가 함께 있는가"를 먼저 확인하라 — 셋 중 둘 이상이 있으면 분리해야 한다.

## 한 줄 요약 — 이것만 기억하면 된다

**AI 코드의 기능 동작 여부보다 팀 패턴 준수, 단일 소스, 에러 처리, SRP 분리를 먼저 점검하는 습관이 품질을 가른다.**

## 나중에 더 깊게 들어가면

- AI 프롬프트에 팀 폴더 구조와 레이어 규칙을 명시해 패턴 위반을 사전에 막는 방법
- TypeScript strict 모드와 ESLint 규칙으로 매직 값과 `any` 사용을 자동 감지하는 설정
- Shared 모듈에 기여할 때 브레이킹 체인지를 추적하는 변경 로그 관리 방법
