> 디스크가 병목이면 LEANN(임베딩 재계산), 운영 단순성이 우선이면 Memvid(단일 파일 패키징). 같은 RAG 문제에 대한 정반대 해법이다.

---

## RAG 저장공간 문제를 왜 해결해야 하는지 감 잡기

RAG(Retrieval-Augmented Generation)는 LLM이 환각을 줄이고 최신 정보를 쓸 수 있게 해주는 기술이다. 핵심은 텍스트를 벡터(숫자 배열)로 변환한 뒤 저장해두고, 질문이 들어오면 비슷한 벡터를 빠르게 찾는 것이다.

문제는 이 벡터 인덱스의 크기다. 원본 텍스트 100GB를 인덱싱하면 인덱스가 150~700GB까지 불어난다. 데이터센터에서는 감당할 수 있지만, 노트북이나 엣지 디바이스에서는 현실적으로 불가능한 규모다.

2025년 두 기술이 이 문제에 정반대로 답했다. Memvid는 "임베딩을 저장하되 하나의 파일로 압축"하고, LEANN은 "임베딩 자체를 저장하지 않고 쿼리할 때 재계산"한다.

초보자는 이렇게 이해하면 된다.

`핵심 흐름: 텍스트 준비 → 벡터 변환(임베딩) → [저장할까 vs 재계산할까] → 유사 검색 → LLM 답변 생성`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 임베딩(Embedding) | 텍스트를 숫자 배열로 바꾼 것. 의미가 비슷한 텍스트는 숫자 배열도 비슷해진다. |
| HNSW | 벡터 검색에 쓰는 그래프 구조. 모든 벡터를 비교하지 않고 빠르게 가장 가까운 벡터를 찾는다. |
| Memvid | 데이터·임베딩·검색 구조를 `.mv2` 파일 하나에 패키징한 RAG 라이브러리. |
| LEANN | 임베딩을 디스크에 저장하지 않고 쿼리 시점에 필요한 노드만 재계산하는 벡터 인덱스. UC Berkeley 등이 개발했다. |
| Progressive Disclosure(LEANN) | HNSW 그래프 탐색 중 실제 방문하는 노드의 임베딩만 계산하는 방식. 전체를 저장할 필요가 없다. |

## 예를 들어 설명하면

N개 청크, d차원 임베딩, FP32(원소당 4바이트) 기준으로 두 방식의 저장공간 차이를 계산하면 다음과 같다.

```
# Memvid (임베딩 저장)
저장공간 = 원본 데이터 + N × d × 4바이트 + HNSW 그래프 메타데이터
예: 100만 청크, 768차원 → 임베딩만 약 3GB + 원본 + 그래프

# LEANN (임베딩 미저장)
저장공간 = 원본 데이터 + 가지치기된 그래프 구조 (목표: 원본의 5% 이하)
예: 원본 500MB → LEANN 인덱스 약 25MB
```

쿼리 지연시간은 반대 방향이다. Memvid는 밀리초 단위 응답이 가능하고, LEANN은 90% recall 기준 2초 내외다.

## 이 단계에서 중요한 판단 기준

먼저 코퍼스 규모와 디바이스 제약을 계산하라 — 저장공간이 절대 제약이면 LEANN, 실시간 응답이 필요하거나 단일 파일 배포가 편리해야 하면 Memvid다.

| 상황 | 권장 | 이유 |
|---|---|---|
| 노트북, 엣지 디바이스 | LEANN | 원본 대비 5% 저장공간 |
| 단일 파일 배포 필요 | Memvid | .mv2 하나로 완결 |
| 하이브리드 검색(BM25+벡터) | Memvid | 기본 내장 |
| 수천만 청크 이상 대규모 | LEANN | 저장공간 선형 증가 회피 |
| 실시간 챗봇 | Memvid | 재계산 오버헤드 없음 |

## 한 줄 요약 — 이것만 기억하면 된다

**임베딩을 저장하느냐(Memvid) vs 쿼리마다 재계산하느냐(LEANN) — 이 선택이 저장공간과 응답 속도를 결정한다.**

## 나중에 더 깊게 들어가면

- LEANN의 2단계 그래프 순회와 동적 배칭이 재계산 지연시간을 줄이는 원리
- Memvid v2.0 Rust 재작성 이후 성능 개선 상세(Python 대비 10~100배)
- 두 기술 모두 2025년 신생 프로젝트이므로 프로덕션 전 직접 벤치마크 필수
