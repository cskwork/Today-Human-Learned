> **TL;DR**
> 기존 코드베이스를 AI에게 분석시켜 암묵적 개발 규칙을 문서로 추출하면, 새 팀원과 AI 코딩 도구 모두 일관된 코드를 작성하는 기반이 생긴다.

---

## 암묵적 규칙 추출을 왜 하는지 감 잡기

팀에는 문서로 적히지 않은 규칙이 있다. Service 레이어에서 직접 SQL을 쓰면 안 된다거나, Controller에서 Entity를 그대로 반환하면 안 된다는 것. 기존 개발자는 경험으로 알지만 새 팀원과 AI 도구는 모른다. 이 암묵적 지식을 AI로 코드에서 직접 추출하면 명시적 문서가 된다.

초보자는 처음에 이렇게 이해하면 된다.

`핵심 흐름: 코드베이스 분석 프롬프트 → AI가 패턴 추출 → 규칙 문서 생성 → AI 도구에 컨텍스트 주입`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 메타 프롬프트 | 코드 자체를 쓰는 프롬프트가 아니라, 코드를 분석해 규칙을 뽑아달라고 지시하는 프롬프트. |
| 일관성 비율 | 분석된 파일 중 특정 패턴을 따른 비율. 70% 이상이면 규칙으로 인정한다. |
| MUST / SHOULD / MAY | 규칙의 강제 수준. MUST는 필수, SHOULD는 권장, MAY는 선택. |
| CLAUDE.md / AGENTS.md | AI 코딩 도구에게 프로젝트 규칙을 주입하는 컨텍스트 파일. 프로젝트 루트에 둔다. |
| 관찰 편향 | 레거시 코드나 임시 구현이 잘못된 규칙으로 인식되는 문제. 팀 리뷰로 검증해야 한다. |

## 예를 들어 설명하면

아래 프롬프트를 AI에게 전달하면 코딩 스타일 규칙을 추출할 수 있다.

```
이 코드베이스를 분석하여 개발 시 준수해야 할 패턴을 추출해주세요.
추측이 아닌 실제 코드에서 관찰되는 패턴만 사용하세요.

분석 영역:
- 네이밍 컨벤션 (클래스, 메소드, 파일)
- 레이어 간 의존성 규칙
- 에러 처리 위치 및 방식
- 데이터 접근 패턴 (ORM/SQL 경계)

출력 형식:
각 규칙에 대해:
- 규칙 명세 (MUST/SHOULD/MAY)
- 코드 증거 (파일명:라인)
- 일관성 비율
- 예외 사항
```

추출된 규칙은 Claude Code라면 `.claude/CLAUDE.md`에, GitHub Copilot이라면 `AGENTS.md`에 기록해 AI 도구에 자동으로 주입한다.

```markdown
# 프로젝트 개발 규칙

## MUST (필수)
- Controller 메소드에 @Valid 어노테이션 사용
- Service 레이어에서 비즈니스 로직 검증
- Repository 패턴을 통한 데이터 접근

## SHOULD (권장)
- Service를 인터페이스와 구현체로 분리

## 금지
- Controller에서 직접 Entity 반환
- 하드코딩된 설정값 사용
```

## 이 단계에서 중요한 판단 기준

추출된 규칙은 반드시 시니어 개발자가 검토한다. AI는 레거시 코드의 나쁜 패턴도 규칙으로 인식할 수 있다. 팀 리뷰 없이 문서를 배포하면 잘못된 관행이 공식화될 수 있다.

## 한 줄 요약 — 이것만 기억하면 된다

**코드베이스에서 AI로 규칙을 뽑고 팀이 검증하면, 암묵적 지식이 AI 도구도 따를 수 있는 명시적 컨텍스트가 된다.**

## 나중에 더 깊게 들어가면

- 비즈니스 도메인 규칙(워크플로우, 상태 변경 시퀀스) 추출 방법
- 코드 변경사항이 추출된 규칙을 위반하는지 자동 검증하는 프롬프트
- 분기별 전체 재추출 및 규칙 갱신 프로세스 설계
