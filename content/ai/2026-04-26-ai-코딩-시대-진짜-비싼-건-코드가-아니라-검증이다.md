> **TL;DR**
> AI가 코드 생성을 자동화할수록, 팀의 핵심 경쟁력은 **빠른 코드 작성에서 검증 능력과 의도 보존**으로 옮겨간다. 마틴 파울러가 2026-04 글에서 정리한 패러다임이다.

---

## 왜 이 글이 중요한지

> "AI가 코드를 많이 만들어낼수록, 팀이 잃기 쉬운 것은 코드 작성 능력이 아니라 시스템을 이해하는 능력."

코드를 빨리 만드는 게 더는 경쟁 우위가 아니게 됐다. 진짜 비싼 건 "이게 맞는 결과인가"를 정의하고 검증하는 일이다.

## 세 가지 부채 (Three Types of Debt)

파울러가 인용한 Margaret-Anne Storey의 개념.

| 부채 | 의미 | AI 시대의 위험 |
|------|------|--------------|
| **Technical Debt** | 코드 구조의 기술적 결함 | 빠르게 생성된 코드의 유지보수 어려움 |
| **Cognitive Debt** | 팀의 이해도 감소 | 시스템 동작 원리를 설명하지 못한다 |
| **Intent Debt** | 목표·제약이 산출물에 미반영 | 원래 설계 의도가 사라진다 |

세 부채는 독립적이지 않고 **서로 영향을 미친다.** Cognitive Debt가 쌓이면 Intent Debt도 함께 쌓이고, 결국 Technical Debt도 안 잡힌다.

## 핵심 인사이트: 검증이 새로운 병목

파울러가 Ajey Gore의 관점을 강조한 한 줄.

> "코드 작성 비용이 거의 0에 수렴하면, 진짜 비싼 것은 검증."

복잡한 도메인일수록 명확하다. 배차 알고리즘을 예로 들면 고객 대기시간·기사 수익 공정성·차량 활용률·지역 교통 상황이 동시에 작동한다. **"올바른 결과"는 AI 도구가 단독으로 판단할 수 있는 게 아닌 비즈니스 결정**이다.

해결책으로 파울러가 꼽는 것은 **좋은 검증 체계, 특히 자동화 테스트**다. 좋은 테스트가 있으면 에이전트도 더 잘 작동한다.

---

## 실습: 배송비 계산

검증 기준을 먼저 정의해본다.

| 조건 | 기대 결과 |
|------|---------|
| 주문금액 ≥ 50,000원 | 배송비 0원 |
| 주문금액 < 50,000원 | 배송비 3,000원 |
| 주문금액 < 0 | 잘못된 입력 처리 |

**핵심**: 함수 구현 전에 "무엇이 맞는 결과인가"를 정의해야 AI가 짠 코드를 평가할 수 있다.

### 최소 구현 (Python 3.12)

```python
def calculate_shipping_fee(order_amount: int) -> int:
    if order_amount < 0:
        raise ValueError("order_amount must be greater than or equal to 0")

    if order_amount >= 50_000:
        return 0

    return 3_000
```

### 테스트

```python
import unittest

class TestShippingFee(unittest.TestCase):
    def test_free_shipping_when_order_amount_is_50000_or_more(self):
        self.assertEqual(calculate_shipping_fee(50_000), 0)
        self.assertEqual(calculate_shipping_fee(70_000), 0)

    def test_shipping_fee_when_order_amount_is_less_than_50000(self):
        self.assertEqual(calculate_shipping_fee(49_999), 3_000)
        self.assertEqual(calculate_shipping_fee(10_000), 3_000)

    def test_invalid_order_amount(self):
        with self.assertRaises(ValueError):
            calculate_shipping_fee(-1)

if __name__ == "__main__":
    unittest.main()
```

`Ran 3 tests in 0.001s → OK`. 이 테스트가 있으면 AI에게 "이 함수 리팩터링해줘"라고 맡겨도 결과의 정합성을 자동으로 평가할 수 있다.

## 모범사례 비교

| 패턴 | 장점 | 주의점 |
|------|------|--------|
| 검증 기준 먼저 정의 | AI 코드의 정답 판단이 쉽다 | 기준이 모호하면 테스트도 모호 |
| 테스트 자동화 | 에이전트 변경사항 빠른 확인 | 테스트가 비즈니스 규칙을 충분히 담아야 |
| 의도 기록 관리 | 다시 이해하기 쉬움 | 문서-코드 동기화 필수 |
| 도메인 용어 정리 | 사람과 AI의 언어 통일 | 코드에 반영되지 않으면 효과 약함 |
| 검증 리뷰 확장 | 스타일 검토 → 결과 타당성 검토 | 리뷰어의 도메인 이해 필수 |

## 마치며

> "앞으로는 무엇을 만들었는지가 아니라, **무엇을 검증했는지**를 물어봐야 한다."

좋은 팀의 미래상은 단순히 많은 코드를 작성하는 팀이 아니라 **올바른 결과를 정의하고 검증할 수 있는 팀**이다.

## 핵심 요약

- **새 경쟁력은 검증**: 코드 생성 비용이 0에 수렴하면서 "무엇이 옳은가"를 정의하고 검증하는 능력이 새 병목
- **세 부채 균형**: Technical · Cognitive · Intent Debt를 모두 관리해야 시스템 건강성 유지
- **TDD + 자동화**: 검증 기준 먼저 정의하고 테스트로 자동화하면 AI 에이전트가 더 효과적으로 작동
