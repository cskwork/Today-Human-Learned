---

## AI 에이전트를 왜 쓰는지 감 잡기

AI 에이전트는 단순히 질문에 답하는 챗봇이 아니다. LLM이 계획을 세우고, 외부 도구(API, 파일, DB)를 호출하고, 결과를 검증한 뒤 다음 단계를 스스로 결정하는 시스템이다. 1년간 5개 스타트업에서 300개의 에이전트를 만든 경험에서 나온 핵심 교훈은 하나다. 가장 정교한 에이전트가 아니라 가장 범위가 좁고 신뢰할 수 있는 에이전트가 실제로 쓰인다.

초보자는 이렇게 이해하면 된다.

`핵심 흐름: 컨텍스트 수집 → 계획 수립 → 도구 실행 → 검증 → 기록 → 다음 단계 결정 또는 중지`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 에이전트 루프 | 에이전트가 작업을 완료할 때까지 계획-실행-검증을 반복하는 순환 구조 |
| RAG (검색 증강 생성) | 모델의 내장 지식 대신 외부 문서를 검색해 컨텍스트로 제공하는 기법 — "올바른 정보를 모델에 먹이는" 방법 |
| 스크래치패드 (Scratchpad) | 에이전트가 작업 중 중간 계산 결과나 계획을 임시로 기록하는 단기 메모리 |
| 멱등성 (Idempotency) | 같은 작업을 여러 번 실행해도 결과가 동일한 성질 — "send_email" 전에 "create_draft"를 쓰는 이유 |
| 인간 루프 (Human-in-the-loop) | 되돌릴 수 없는 작업(이메일 전송, 결제 등) 전에 사람의 승인을 요구하는 설계 패턴 |

## 예를 들어 설명하면

"주간 판매 요약 작성 후 PM에게 이메일 전송" 에이전트의 설계 예시다.

```
입력: CRM API, 문서 폴더, 캘린더
도구: HTTP 클라이언트, 파일 읽기, 이메일 초안 API, 벡터 검색

정책:
- 인간 승인 없이 이메일 전송 금지
- 최대 도구 호출 6회, 호출당 30초 타임아웃

관찰성:
- 추적 ID, 실행 단계, 도구 입출력, 지연 시간, 성공 여부를 모두 기록
```

이 설계에서 핵심은 "이메일 전송 금지" 정책이다. 에이전트가 초안을 만들고 사람이 최종 전송을 누른다. 이 한 줄의 게이트가 사용자 신뢰를 만든다.

## 이 단계에서 중요한 판단 기준

에이전트를 설계할 때 "이 작업이 되돌릴 수 없는가"를 먼저 물어라 — 그렇다면 반드시 인간 승인 단계를 넣어야 한다.

## 한 줄 요약 — 이것만 기억하면 된다

**루프는 작게, 컨텍스트는 정확하게, 인간을 루프 안에 유지하는 것이 프로덕션 에이전트의 세 가지 조건이다.**

## 나중에 더 깊게 들어가면

- 다중 에이전트 시스템에서 오케스트레이터와 서브에이전트를 분리하는 설계 방법
- 에이전트 루프에 타임아웃, 최대 단계 수, 안전 모드(읽기 전용)를 추가하는 가드레일 구현
- 음성 에이전트(STT → LLM → TTS 파이프라인)에서 왕복 지연 300ms~1.5초를 달성하는 최적화 방법
