# IoC와 DI — 제어의 역전과 의존성 주입의 차이

> **TL;DR**
> IoC는 "객체 생성 권한을 프레임워크에 넘긴다"는 설계 원칙이고, DI는 그것을 실현하는 구체적인 방법이다.

---

## IoC와 DI를 왜 쓰는지 감 잡기

코드를 직접 짜다 보면 클래스 안에서 `new PaymentService()`처럼 다른 객체를 직접 만드는 일이 자연스럽다. 그런데 이러면 두 클래스가 단단히 묶인다. `PaymentService`를 바꾸려면 이를 쓰는 모든 클래스를 뜯어고쳐야 하고, 테스트할 때 가짜 객체(Mock)를 끼워 넣기도 어렵다.

IoC(Inversion of Control, 제어의 역전)는 이 생성 권한을 개발자가 아닌 스프링 컨테이너에 넘기는 것이다. DI(Dependency Injection, 의존성 주입)는 그 컨테이너가 "필요한 객체를 생성해서 외부에서 꽂아준다"는 구체적인 실천 방법이다.

`핵심 흐름: 개발자가 @Service 선언 → 스프링 컨테이너가 Bean 생성 → 의존 관계 자동 주입 → 개발자는 비즈니스 로직만 작성`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| IoC | 객체를 누가 만들지에 대한 제어권을 프레임워크에 양도하는 개념 |
| DI | 필요한 객체를 외부(스프링)가 만들어서 생성자·필드로 넣어주는 방법 |
| Bean | 스프링 컨테이너가 관리하는 객체 단위 |
| 결합도 | 두 클래스가 얼마나 서로에게 의존하는지의 정도 |
| 생성자 주입 | DI 방식 중 가장 권장되는 형태 — 생성자 파라미터로 의존 객체를 받음 |

## 예를 들어 설명하면

DI 적용 전후를 나란히 보면 차이가 명확하다.

```java
// DI 없음 — OrderService가 PaymentService를 직접 생성
public class OrderService {
    private PaymentService paymentService = new PaymentService(); // 결합 고정
}

// DI 적용 — 스프링이 PaymentService를 만들어서 주입
@Service
public class OrderService {
    private final PaymentService paymentService;

    @Autowired
    public OrderService(PaymentService paymentService) { // 외부에서 받음
        this.paymentService = paymentService;
    }
}
```

스프링은 `@Service`가 붙은 두 클래스를 모두 Bean으로 등록한 뒤, `OrderService` 생성자에 `PaymentService` Bean을 자동으로 넣어준다.

## 이 단계에서 중요한 판단 기준

클래스 안에서 `new`로 다른 서비스 객체를 만들고 있다면, 그 순간이 DI로 전환해야 할 신호다 — 테스트할 때 Mock을 넣을 수 없기 때문이다.

## 한 줄 요약 — 이것만 기억하면 된다

**IoC는 설계 원칙이고 DI는 구현 수단이다 — 스프링 컨테이너가 객체를 만들고 연결해주므로 개발자는 `new` 대신 어노테이션만 붙이면 된다.**

## 나중에 더 깊게 들어가면

- `@Configuration` + `@Bean`으로 직접 Bean 등록하는 방법
- 순환 의존성(Circular Dependency)이 생기는 이유와 해결책
- 필드 주입 vs 생성자 주입 vs 세터 주입의 트레이드오프
