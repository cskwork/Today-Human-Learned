# Java 디자인 패턴 — 객체를 만들고 연결하는 검증된 설계 방식

> **TL;DR**
> 디자인 패턴은 반복되는 설계 문제의 검증된 해법이며, 생성·구조·행위 세 범주로 나뉜다.

---

## 디자인 패턴을 왜 쓰는지 감 잡기

코드를 짜다 보면 비슷한 문제가 반복된다. "객체를 어떻게 만들지?", "서로 다른 인터페이스를 어떻게 연결하지?", "상태 변화를 다른 객체에 어떻게 알리지?" 디자인 패턴은 이런 문제에 대해 수십 년간 많은 개발자가 검증한 해법을 이름 붙여 정리한 것이다. 코드를 복사하는 게 아니라 설계 아이디어를 빌리는 것이다.

초보자는 처음에 이렇게 이해하면 된다.

`핵심 흐름: 문제 인식 → 해당 범주의 패턴 선택 → 인터페이스/추상화로 구현`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 생성 패턴 | 객체를 어떻게 만들지를 다루는 패턴 모음 |
| 구조 패턴 | 클래스나 객체를 어떻게 조합할지를 다루는 패턴 모음 |
| 행위 패턴 | 객체 간 소통과 책임 분배를 다루는 패턴 모음 |
| 인터페이스 | 구현 없이 "무엇을 할 수 있는가"만 정의하는 계약 |
| 싱글톤 | 앱 전체에서 인스턴스가 딱 하나만 존재하도록 보장하는 패턴 |

## 예를 들어 설명하면

세 범주의 대표 패턴을 한 줄씩 정리한다.

| 범주 | 패턴 | 한 줄 설명 |
|---|---|---|
| 생성 | 싱글톤 | DB 커넥션 풀처럼 앱 전체에서 인스턴스 하나를 공유 |
| 생성 | 팩토리 메서드 | 부모는 "만들어라"고 선언하고, 자식이 실제 객체를 결정 |
| 생성 | 빌더 | 복잡한 객체를 단계별로 조립. 읽기 쉬운 코드 유지 |
| 구조 | 어댑터 | 맞지 않는 인터페이스 사이에 변환 클래스를 끼워 연결 |
| 구조 | 퍼사드 | 복잡한 서브시스템을 단순한 창구 하나로 노출 |
| 행위 | 옵저버 | 이벤트 발생 시 등록된 리스너들을 자동으로 호출 |
| 행위 | 전략 | 동작 로직을 교체 가능한 클래스로 분리해 런타임에 선택 |

싱글톤 구현 중 멀티스레드 환경에서 가장 안전하고 일반적으로 권장하는 방식은 홀더 패턴이다.

```java
public class Something {
    private Something() {}

    private static class LazyHolder {
        public static final Something INSTANCE = new Something();
    }

    public static Something getInstance() {
        return LazyHolder.INSTANCE;
    }
}
```

JVM이 클래스 로딩 시점에 초기화를 보장하므로 별도의 동기화 코드가 필요 없다.

## 이 단계에서 중요한 판단 기준

패턴을 먼저 고르려 하지 말고, 현재 겪는 설계 문제를 먼저 명확히 한 뒤 어울리는 패턴을 찾는다. 패턴은 목적이 아니라 수단이다.

## 한 줄 요약 — 이것만 기억하면 된다

**디자인 패턴은 설계 문제의 이름 붙은 해법이며, 패턴 이름을 알면 팀원과 같은 언어로 설계를 논할 수 있다.**

## 나중에 더 깊게 들어가면

- SOLID 원칙: 디자인 패턴이 왜 이렇게 설계됐는지 이해하는 토대
- 추상 팩토리와 팩토리 메서드의 차이: 객체 패밀리 vs 단일 객체 생성
- 컴포지트 패턴: 트리 구조에서 단일 객체와 복합 객체를 동일하게 다루는 방법
