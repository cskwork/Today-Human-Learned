# RAG와 문맥 검색 — 청크에 배경을 붙이면 정확도가 달라진다

> **TL;DR**
> 기존 RAG의 "문맥 손실" 문제는 각 청크에 배경 설명을 추가하는 Contextual Retrieval로 49% 줄일 수 있다.

---

## 이 주제를 왜 쓰는지 감 잡기

RAG에서 문서를 청크로 쪼개면 원래 문맥이 사라진다. "매출이 3% 증가했습니다"라는 문장은 단독으로는 어떤 회사인지, 언제 데이터인지 알 수 없다. 이 상태로 검색하면 정확도가 떨어지고, LLM이 받는 컨텍스트도 불완전해진다. 문맥 검색(Contextual Retrieval)은 청크를 저장하기 전에 배경 정보를 덧붙여 이 문제를 해결한다.

`핵심 흐름: 원본 문서 + 청크 → LLM이 배경 설명 생성 → 설명이 붙은 청크 저장 → 검색 → LLM 응답`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 청크(Chunk) | 검색 단위로 쪼갠 문서 조각. 쪼개면서 앞뒤 문맥이 잘린다 |
| 문맥 손실 | 청크만 보면 "누가, 언제, 어디서"가 사라지는 현상 |
| Contextual Retrieval | 각 청크에 "이 내용이 어느 문서의 어느 부분인지" 설명을 자동 추가하는 기법 |
| 재순위화(Reranking) | 검색 결과를 한 번 더 관련도 순으로 정렬하는 단계. Contextual Retrieval과 함께 쓰면 검색 실패율 67% 감소 |
| 프롬프트 캐싱 | 동일한 긴 프롬프트를 반복 호출할 때 비용을 줄이는 기술. 대규모 문맥화 작업의 비용을 크게 낮춘다 |

## 예를 들어 설명하면

배경 설명을 붙이기 전과 후의 차이를 보면 이해가 빠르다.

```
변경 전 (문맥 손실):
"회사의 매출은 전 분기 대비 3% 증가했습니다."

변경 후 (문맥 보존):
"이 내용은 ACME 사의 2023년 2분기 실적 보고서에서 발췌했습니다.
이전 분기 매출은 3억 1,400만 달러였습니다.
회사의 매출은 전 분기 대비 3% 증가했습니다."
```

구현 방향은 단순하다. 청크를 임베딩 DB에 저장하기 전, LLM에게 "이 청크가 원본 문서의 어떤 맥락에 있는지 한 문단으로 설명해줘"라고 요청한다. 반환된 설명을 청크 앞에 이어붙인 뒤 저장한다.

## 이 단계에서 중요한 판단 기준

문맥화 과정에서 LLM을 대량 호출하면 비용이 커진다. 프롬프트 캐싱을 지원하는 모델을 쓰면 반복 호출 비용을 대폭 줄일 수 있으므로, 비용을 추산한 뒤 도입 여부를 결정하라.

## 한 줄 요약 — 이것만 기억하면 된다

**청크를 저장하기 전에 배경 설명을 붙이면 검색 정확도가 크게 올라간다.**

## 나중에 더 깊게 들어가면

- BM25와 벡터 검색을 결합한 하이브리드 Contextual Retrieval
- 임베딩 모델별 성능 비교 (Voyage, Gemini 등)
- 청크 크기 튜닝이 문맥화 효과에 미치는 영향
