# RAG 시스템 설계 — LLM에게 "진짜 문서"를 읽히는 법

> **TL;DR**
> RAG는 LLM이 학습 데이터에 없는 최신·내부 문서를 참조해 답할 수 있게 하는 구조로, 문서를 잘게 쪼개 벡터로 저장한 뒤 질문과 가장 가까운 조각만 골라 LLM에 넘긴다.

---

## RAG를 왜 쓰는지 감 잡기

LLM은 학습 시점 이후의 정보는 모른다. 사내 정책 문서나 최신 제품 매뉴얼 같은 내부 자료도 당연히 모른다. 이럴 때 LLM에게 "관련 문서를 먼저 찾아서 읽고 답해"라고 시키는 방식이 RAG(Retrieval-Augmented Generation)다.

RAG는 두 단계로 나뉜다. 첫 번째는 오프라인에서 한 번만 실행하는 색인(Ingestion) 단계다. 두 번째는 사용자가 질문할 때마다 실행하는 검색·생성(Query) 단계다.

초보자는 처음에 이렇게 이해하면 된다.

`핵심 흐름: 문서 로드 → 청크 분할 → 벡터 저장 | 질문 → 유사 청크 검색 → LLM 답변`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 임베딩(Embedding) | 텍스트를 숫자 벡터로 변환한 것. "의미가 비슷한 문장은 벡터 공간에서 가까이 있다"는 원리를 이용한다 |
| 청크(Chunk) | 문서를 LLM이 한 번에 처리할 수 있는 크기로 잘라낸 조각. 크기와 겹침(overlap) 설정이 품질을 좌우한다 |
| 벡터 DB | 벡터를 저장하고 "가장 가까운 벡터 k개"를 빠르게 찾아주는 특수 데이터베이스 (ChromaDB, FAISS 등) |
| k-NN 검색 | 질문 벡터와 가장 가까운 k개의 문서 청크를 찾는 작업 — RAG의 핵심 "검색" 단계 |
| 프롬프트 증강 | 검색된 청크를 사용자 질문과 함께 "이 맥락만 참고해서 답해라"는 형태로 LLM에 전달하는 것 |

## 예를 들어 설명하면

사내 정책 문서 100페이지가 있다고 하자. 사용자가 "휴가 신청 절차가 어떻게 돼?"라고 질문한다.

1. 색인 단계(미리 실행): 100페이지를 1,000자 단위 청크로 자르고, 각 청크를 임베딩 모델로 벡터화해 ChromaDB에 저장한다.
2. 검색 단계(질문마다): "휴가 신청 절차" 질문도 같은 모델로 벡터화한다. ChromaDB에서 k-NN 검색으로 가장 관련 있는 청크 5개를 꺼낸다.
3. 생성 단계: 아래 형태로 LLM을 호출한다.

```
맥락:
[검색된 청크 1~5]

질문: 휴가 신청 절차가 어떻게 돼?

위 맥락만 참고해서 답해라.
```

LLM은 학습 데이터가 아닌 실제 문서를 근거로 답하므로 환각(Hallucination)이 줄어든다.

## 이 단계에서 중요한 판단 기준

청크 크기가 너무 크면 맥락이 뭉개지고, 너무 작으면 의미가 잘린다 — 1,000자 전후, 100자 겹침에서 시작해 실제 품질을 보면서 조정한다.

## 한 줄 요약 — 이것만 기억하면 된다

**RAG는 LLM에 "정답지"를 먼저 찾아서 건네주는 구조다 — 색인을 잘 만들수록 답변 품질이 올라간다.**

## 나중에 더 깊게 들어가면

- 하이브리드 검색: BM25 키워드 검색과 시맨틱 벡터 검색을 함께 쓰는 방법
- 재순위화(Reranking): k-NN으로 뽑은 후보를 별도 모델로 다시 정렬해 정확도를 높이는 기법
- 평가 파이프라인: RAGAs 같은 도구로 검색 품질과 답변 품질을 수치로 측정하는 방법
