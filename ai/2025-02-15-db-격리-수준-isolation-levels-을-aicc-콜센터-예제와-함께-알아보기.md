# DB 격리 수준(Isolation Level) — 콜센터 예제로 이해하기

> **TL;DR**
> 격리 수준은 "동시에 여러 트랜잭션이 실행될 때 서로 얼마나 보이게 할 것인가"를 결정하는 설정이며, 높을수록 안전하고 낮을수록 빠르다.

---

## 격리 수준을 왜 쓰는지 감 잡기

콜센터에서 상담사 A가 고객 정보를 수정하는 동안, 상담사 B가 같은 고객 정보를 조회한다. 이때 B가 보는 정보는 수정 전인가, 수정 후인가? 아직 저장이 확정되지 않은 값인가? 이 질문에 대한 답이 격리 수준이다. 데이터베이스는 동시성(여러 트랜잭션 동시 처리)과 무결성(데이터 정확성) 사이에서 절충점을 골라야 하고, 그 선택지가 4단계 격리 수준이다.

초보자는 처음에 이렇게 이해하면 된다.

`핵심 흐름: 트랜잭션 A 실행 중 → 트랜잭션 B가 A의 데이터에 접근 → 격리 수준이 "무엇을 보여줄지" 결정`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| Dirty Read | 아직 커밋되지 않은(확정 안 된) 데이터를 다른 트랜잭션이 읽어버리는 현상 |
| Non-Repeatable Read | 같은 트랜잭션에서 같은 행을 두 번 조회했는데 결과가 달라지는 현상 |
| Phantom Read | 같은 조건으로 조회했는데 이번엔 없던 행이 나타나거나 사라지는 현상 |
| MVCC | 다중 버전 동시성 제어. 데이터를 잠그지 않고 버전을 나눠 읽기를 허용하는 방식 |
| 커밋(Commit) | 트랜잭션을 확정해서 변경 내용을 데이터베이스에 영구 반영하는 동작 |

## 예를 들어 설명하면

4단계 격리 수준을 콜센터 상황에 대입하면 이렇게 된다.

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read | 콜센터 적합성 |
|---|---|---|---|---|
| READ UNCOMMITTED | 발생 | 발생 | 발생 | 실무 부적합 |
| READ COMMITTED | 방지 | 발생 | 발생 | 일반 상담 업무에 충분 |
| REPEATABLE READ | 방지 | 방지 | 발생 | MySQL InnoDB 기본값 |
| SERIALIZABLE | 방지 | 방지 | 방지 | 금융 거래 등 고무결성 요구 시 |

READ UNCOMMITTED는 상담사 A가 롤백하기 전 데이터를 상담사 B가 읽어버리는 사고를 유발하므로 실무에서 쓰지 않는다. 콜센터 대부분의 업무는 READ COMMITTED로 충분하다.

MySQL에서 세션 단위로 격리 수준을 설정하는 방법은 이렇다.

```sql
-- 현재 격리 수준 확인
SELECT @@tx_isolation;

-- 세션 격리 수준 변경
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

## 이 단계에서 중요한 판단 기준

격리 수준을 높이면 안전하지만 락(Lock)이 늘어 동시 처리량이 줄어든다. 트래픽이 많은 콜센터에서 SERIALIZABLE을 전체 적용하면 응답 지연이 급격히 늘어난다. 업무 유형별로 격리 수준을 다르게 적용하는 것이 현실적이다.

## 한 줄 요약 — 이것만 기억하면 된다

**격리 수준은 "동시성과 정확성" 사이의 트레이드오프를 업무 요구에 맞게 조정하는 설정값이다.**

## 나중에 더 깊게 들어가면

- MVCC 내부 동작 — InnoDB가 버전을 어떻게 관리해서 READ COMMITTED를 구현하는가
- 갭 락(Gap Lock) — REPEATABLE READ에서 Phantom Read를 줄이기 위해 MySQL이 쓰는 방식
- 분산 데이터베이스의 격리 수준 — 여러 서버에 걸친 트랜잭션에서 격리를 어떻게 보장하는가
