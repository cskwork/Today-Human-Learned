# "노룩 코드"의 위험성: 에이전트에 모든 걸 맡겼을 때 벌어지는 일들

> **TL;DR**
> 에이전트 코딩은 신기능 구현을 빠르게 해주지만, 검토 없이 맡기면 보안 유출, 코드 품질 저하, 개발 역량 소실이라는 세 가지 대가를 치른다.

---

## "노룩 코드"가 왜 문제인지 감 잡기

에이전트에게 "이 기능 만들어줘"라고 하고 결과만 확인하는 방식을 노룩 코드(no-look coding)라고 부른다. 처음에는 빠르게 돌아가는 것처럼 보인다. 그런데 시간이 지나면 세 가지 문제가 쌓인다.

첫째, 보안 정보가 새어나간다. API 키, 비밀번호 같은 민감 정보가 LLM에 그대로 넘어가도 모른다. 둘째, 유지보수 비용이 폭발한다. 에이전트가 만든 코드의 버그를 수정하는 이른바 "바이브 디버깅"에는 신규 개발 대비 10~100배 시간이 걸릴 수 있다. 셋째, 직접 코드를 보지 않으니 개발 감각이 떨어진다.

초보자는 처음에 이렇게 이해하면 된다.

`핵심 흐름: 에이전트 위임 → 중간 검토 없음 → 품질 저하 누적 → 수정 비용 폭발`

## 외워야 할 핵심 용어 5개

| 용어 | 초보자식 설명 |
|---|---|
| 노룩 코드 | 에이전트 출력을 검토 없이 그대로 사용하는 습관 |
| 바이브 디버깅 | 에이전트가 만든 코드의 버그를 다시 에이전트로 고치는 과정. 원인 파악 없이 증상만 패치하는 악순환 |
| 형상 관리 (Git) | 코드 변경 이력을 기록해서 문제 발생 시 이전 상태로 돌아갈 수 있게 하는 시스템 |
| 생산성 착시 | 에이전트 코딩이 "모든 일을 빠르게 해결한다"는 잘못된 인식. 실제 품질과 유지보수 난이도는 숨겨진다. |
| 역량 퇴화 | 에이전트에 의존할수록 직접 코딩 능력이 줄어드는 현상. PM 역할로 이동하는 것과 유사하다. |

## 예를 들어 설명하면

실제 사례 패턴은 이렇다. 개발자가 에이전트에게 인증 기능을 맡긴다. 에이전트는 동작하는 코드를 만든다. 개발자는 테스트 없이 커밋한다. 3개월 뒤 다른 기능을 수정하다가 인증 로직이 깨진다. 에이전트에게 수정을 맡기면 다른 부분이 깨진다. 이미 원본 구조를 아무도 이해하지 못하는 상태다.

막을 수 있는 방법은 간단하다.

```
# 에이전트 코딩 체크리스트
1. 민감 정보(API 키, 비밀번호)는 에이전트 프롬프트에서 제거한다
2. 에이전트 출력물을 직접 읽고 이해한 후 커밋한다
3. 정상 동작하는 상태를 git commit으로 즉시 기록한다
4. 어려운 업무는 고성능 모델을 쓴다. 토큰 비용 절약이 수정 비용을 키운다
```

## 이 단계에서 중요한 판단 기준

에이전트가 만든 코드를 내가 동료에게 설명할 수 없다면, 그 코드는 아직 커밋할 수 없는 코드다.

## 한 줄 요약 — 이것만 기억하면 된다

**에이전트는 도구이고 책임은 여전히 개발자에게 있다. 출력 검토와 Git 기록 없이 쓰는 에이전트 코딩은 기술 부채를 빠르게 쌓는 방법이다.**

## 나중에 더 깊게 들어가면

- 에이전트 코딩에서 코드 리뷰를 자동화하는 방법
- LLM 컨텍스트에 민감 정보를 노출하지 않는 설계 패턴
- 에이전트 출력 품질을 평가하는 지표와 기준
